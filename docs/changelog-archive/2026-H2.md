<a id="2026-09-11-tutor-an-instruction-that-could-not-be-obeyed"></a>

## Tutor — an instruction the model could not obey, on every run — backend — 2026-09-11

The Tutor's system prompt told the model: *"On a word the learner missed (or a hard context-stage
card), call `get_example_sentence` to ground it in a real sentence from their reading."*

That tool was deleted with the retrieval spine. `ToolRegistry.SchemasFor` skips an unknown name
**silently** — deliberately, so a half-configured agent still runs — so the model was never offered
it, nothing failed, and nothing logged. Every planning run since has paid for an instruction that
could only be ignored. An instruction that cannot be obeyed is worse than a missing feature.

Removed from the allowed-tools list and from the prompt, along with the eval's stub for it and two
doc comments still describing it as live.

**Grounding is not lost, and getting it back needs no tool.** `VocabularyWord.Sentence` already holds
the sentence each word was saved from, and `get_due_vocabulary` already reports `hasSentence` per
card — the sentence itself belongs in that same projection, which costs one round-trip *fewer* than a
dedicated tool did.

**The guard matters more than the fix.** `AgentAllowedToolsExistTests` reflects over every agent's
`AllowedTools` and asserts each name is implemented by a real `ITool`, reading names off the concrete
types rather than booting the API's composition root. It is verified by mutation — putting the dead
name back turns it red — and it includes a check that the reflection found any agents at all, because
a reflection-driven theory that finds nothing passes vacuously, which is this style of test's own
failure mode.

<a id="2026-09-10-insights-a-conclusion-can-be-removed"></a>

## Insights — a conclusion filed against the wrong chapter can finally be removed — backend, web, mobile — 2026-09-10

Saving again replaces the insight for the same chapter, so a *poor* conclusion about the right
chapter fixes itself on the next pass. A conclusion filed against the **wrong** chapter does not:
nothing ever revisits that slot, the assistant only overwrites the chapter it meant, and no client
could remove it. It was permanent.

`DELETE /me/insights/{id}`, reader-only. 404 rather than 403 for someone else's id, so the endpoint
cannot be used to learn that an id exists. Hard delete — the entity's own stance is a конспект, not a
log, and a `deleted_at` would have to enter both partial unique index filters, which is where the
`NULLS NOT DISTINCT` rule protecting the book-level row lives.

**Deliberately not an MCP tool.** `save_insight`'s worst case is one bad paragraph the reader removes
in a tap. A delete tool's worst case is a year of конспект gone, driven by a stateless bridge that
cannot confirm intent, against a table with no soft-delete and no trash. That asymmetry is
categorical, not a matter of degree.

On both clients the affordance sits beside the chapter label rather than in a corner of its own —
removing a note is a rare correction, not something the panel should advertise. A delete the server
refuses leaves the row on screen, because it is still there.

This came out of a three-way consilium on insight categories, which agreed on the delete and
disagreed on everything else; what it settled and what it left for the owner is written up in
[`assistant-handoff.md`](../05-features/assistant-handoff.md).

**Follow-up, same day — the categories were dropped before they were built.** The plan called for
four fixed categories (Conclusions · Watch for · Discussed · Questions) with tabs. Three independent
readings of the code disagreed about them and converged on one question for the owner: *when you come
back in a month, do you open one book or all of them?* The answer was one book — and per-book
retrieval is served by a chapter label and reading order, both of which already shipped. No column,
no migration, no tabs. What the panel was genuinely missing was a **date**: a конспект is read months
later, and without one it cannot answer "is this what I thought then, or what I think now". That is
one pure function (`insightDateLabel`), absolute rather than relative, ISO so it is unambiguous in
every locale. The enum is revisitable if retrieval ever turns cross-book — the one shape that really
needs a typed field.

<a id="2026-09-10-progress-the-same-action-writes-the-same-thing"></a>

## Progress — the same action writes the same thing, and the first write stops being the exception — backend, web, mobile, shared — 2026-09-10

Four of the ten progress-path defects recorded while tracing the assistant handoff, closed. Two of
the remaining six turn out not to be worth fixing, and saying why is the more useful outcome than
fixing them would have been.

**"Mark as finished" wrote two different things.** Web sent the `{"type":"end"}` sentinel; mobile,
from the same menu on the same kind of book, sent `scroll:<lastSlug>:0` — so a book marked finished
on the phone reopened at the top of its last chapter and the same book marked finished in the browser
did not. The sentinels now have one definition (`packages/shared/src/reader/progressLocators.ts`),
both clients import it, and mobile's action goes through a `markProgressFinished` that does not
pretend to know a scroll offset it was never told.

**The first write for a book was the one that skipped the rules.** `PUT /me/progress/{editionId}`
had two code paths writing one row: an update that checked `ProgressUnit.IsTrusted` before storing a
percentage, and an insert that assigned `request.Percent` by hand. So the very first write for an
edition kept an untrusted number every later write would have refused — and a book finished in a
single write never got a `CompletedAt`, because the insert did not record completion either. The
insert now builds an empty row and hands it to the same `ApplyProgressUpdate`.
`ProgressUnitEndpointTests` covers it from outside, because which branch runs is a database fact no
unit test can choose.

**`ReadingProgressDto` existed twice in TypeScript** with nothing linking the copies. Web now imports
the shared one and re-exports it, so every `from '../api/auth'` import keeps working against a single
definition.

**Two are deliberately left alone.**

- **`LocatorKind` on the catalog path.** The guard exists because an upload can be read two ways —
  Original-layout PDF (`page:<n>`) and reflow (`scroll:…`). A catalog edition has no PDF and no second
  space. Adding it would break exactly what it was meant to protect: `MayReplace` refuses any write
  whose locator belongs to no space, and the mark-as-read sentinel above is precisely that.
- **`markAsUnread` never lowering `MaxChapterNumber`.** Its only reader was the RAG spoiler gate,
  deleted with `ask_book`. The column is now written by two paths and read by none — a drop
  candidate, not a bug, and dropping a column on a production table to correct a value nobody reads
  is the more expensive mistake.

**And a tap that did nothing now says so.** "Talk this book over" swallowed `openURL`'s rejection on
purpose — there is nothing useful to say about "you have no browser". But the outcome a reader sees
is a button that does nothing, which is indistinguishable from a broken one. It shows a toast.

**Five dead web modules and one stylesheet deleted** — `fuzzyMatch`, `wordAtPoint`,
`useOfflineDownload`, `useSwipe`, `useVocabLevel`, `native-language-picker.css`. No importers, and
none on `main` either. Three of them were listed as live in `CLAUDE.md`'s own hook inventory.
<a id="2026-09-10-mcp-the-assistant-can-see-where-you-are"></a>

## MCP — the assistant can see where you are, and record where you got to — backend — 2026-09-10

Thirteen tools could read any book in the library and write conclusions back into it. Not one of them
could answer *where the reader is*. The position existed on the server the whole time; the only way it
ever surfaced was as `ask_book`'s spoiler refusal, and that tool is gone. So a conversation about a
book began from nothing every time: which book, which chapter, how far — all of it re-typed by the
person who had just been reading it.

Three tools, no migration.

**`get_my_reading` takes no arguments.** That is the point of it: every other tool needs an id, and
nothing produced one. It answers over `GET /me/library/shelves`, which has always returned both book
kinds in one response with titles, authors and progress already joined, and which no MCP tool called.
Each row hands back the id the other tools actually take — `bookId` for an upload, `editionId` *and*
`slug` for a catalog book — because handing back the wrong one reads as "book not found" three calls
later, far from the cause. The shelf is capped and filtered to in-progress, so `GET /me/books`
supplies the rest, including books never opened.

**`get_book_progress`** answers the same question for one book: the chapter you stopped in, how far
in, whether you finished it. A book never opened 404s upstream, which is an answer, not a failure —
reporting it as an error would have the model tell a reader their library is broken.

**`set_book_progress` closes the loop the other way.** You listened to chapter two in Spotify; the app
should know. It takes a chapter *slug*, and what it does with it is the part worth stating: finishing
a chapter resumes you at the **start of the next one** — not back in what you just finished — using
the app's own two sentinels (`{"type":"start"}`, and `{"type":"end"}` on the last chapter, which is
exactly what "mark as read" writes). Progress becomes chapters-finished over chapters-total, declared
as a book fraction, because the catalog path *assigns* that column: a write carrying no number blanks
the one that was there.

**Four defects had to be fixed for any of this to be true.**

- **A chapter slug was stored unvalidated.** `UserBookService.UpsertProgressAsync` assigned
  `request.ChapterSlug` raw. An assistant that invented a slug had it stored verbatim, and every later
  read — resume, shelf card, reader — resolved it to nothing. The bookmark path in the same service
  has always checked. Progress never did.
- **A refusal reported success.** `LocatorSpace.MayReplace` returning false dropped the whole write
  and answered `(true, null)`. That was defensible while the only callers were readers' apps, which
  cannot act on an error and would retry into it. It stopped being defensible the moment an assistant
  became a caller: a 200 that stored nothing has it tell a person their progress was recorded.
- **`get_book`'s chapter projection dropped the chapter id** — while `save_highlight`'s own
  description told the model to take `chapterId` "from `get_book`". Following that instruction was
  impossible. The id is back, which is also what lets the catalog write resolve a slug to the GUID the
  route requires.
- **The shelf selected `chapterSlug` and threw it away**, because `LibraryShelfItemDto` had nowhere to
  put it. One optional field at the end of the record; the service already had the value in all three
  projections.

Proven against the running bridge rather than only the stubs: mint a key, `POST /mcp`, `get_my_reading`
returns the shelf **with titles**, `set_book_progress` moves the position to the next chapter, the next
`get_my_reading` shows it moved, and an invented slug comes back as an error instead of a silent save.

**Tool count is asserted in four places** (`McpManifestDriftTests`, `McpStdioSmokeTests`,
`McpOverTheWireTests`, `McpManifestEndpointTests`) and every description is mirrored character for
character into `Contracts/Mcp/McpManifest.cs`, which the API serves and the drift test compares.

<a id="2026-09-08-mcp-the-book-opens-to-your-assistant-and-the-conclusions-come-back"></a>

## MCP — the book opens to your assistant, and the conclusions come back — backend, web — 2026-09-08

A colleague filed a small bug: MCP could not reach a book the user had uploaded. It was real, and the
fix it proposed was not buildable. Chasing why produced a bigger answer about what TextStack is.

**The bug, and why the spec could not be followed.** Step one of the spec — add a library-search
endpoint — was already done: `GET /me/library/search` has existed, scoped by `user_id` in SQL, and
the web already uses it. Step two asked the tool to return an `editionId` for each hit. **An upload
does not have one and cannot be given one.** `UserBook` and `Edition` are separate aggregates with
separate chapter and chunk tables, and the non-polymorphism is documented on the entity itself. Built
as written, every id would 404 in `ask_book` and return a silent empty list from
`list_my_highlights` — a wrong id that reads like an empty library. The identifier is `bookId`, and
the tool descriptions now say so in as many words.

**Why "I connected Claude Code and got nothing" was not a prompt problem.** Reconnaissance on
production: 75 uploaded books, **3 indexed**; 1,423 catalog editions, **4** with chunks. An
unindexed book returns `insufficient` *without calling the LLM*. `ask_book` was answering correctly
about a corpus that was 96% empty. Cost was never the constraint — every conversational feature
together has spent five cents; $4.14 of the $4.25 total is PDF vision parsing.

**Six tools for the uploaded half, needing no index at all.** `search_my_library` (Postgres FTS over
`user_chapters.search_vector`, built at upload), `get_my_book`, `get_my_chapter`,
`save_my_highlight`, `list_my_book_highlights`. Measured on production: **73 of 75 books have
chapters and 72 have real text**, so this works on essentially the whole library today, with no
embeddings and no vision parse. `search_books`' description now says PUBLIC catalog and names its
counterpart, because two search tools whose names differ by `_my_` is not enough for a model under
pressure.

**And then the part that is not a bug fix.** We are not building the chat. A reader's assistant
already holds their profile, their memory and a year of conversation; that cannot be copied here and
competing with it from an empty corpus is not a plan. So: **the reasoning happens there, the result
comes home.** New entity `BookInsight` (table `book_insight`) plus `save_insight` / `get_my_insights`
and `GET|POST /me/insights`. A conclusion hangs on the book's spine — a chapter slug, or nothing for
the whole book — the way every other piece of user markup already does.

A catalog, not a transcript: a transcript is ordered by time and useless to return to, because the
conclusion you want is in the fortieth message. A study конспект is therefore an *assembly* of these
in reading order rather than a frozen document, which is why one insight is kept per
(user, book, chapter) and a save replaces. That upsert has a Postgres trap in it: by default NULLs in
a unique index are distinct from one another, and `chapter_slug IS NULL` is the book-level
overview — the single row most likely to be rewritten, and so the only one a default index would
fail to protect. The index is `NULLS NOT DISTINCT`, and an integration test says so.

The key is the **slug**, not the chapter id: re-ingestion deletes and recreates every chapter, so a
`chapterId` comes unstuck. The same lesson as [ADR-015](../01-architecture/adr/ADR-015-reader-position-is-logical.md),
learned the same week. Chapter number and title are resolved from the slug **at read time**, so a
re-ingest that renumbers chapters cannot leave a stale ordinal behind, and a slug that no longer
resolves keeps its text and sorts last rather than vanishing.

**On the book page**, a "What you've worked out" section renders those conclusions above the chapter
list — coming back to a book, what you already concluded beats the table of contents — and a "Talk
this book over" pair of links opens a new Claude or ChatGPT conversation with a brief already
written. That is a link, not an integration, and it is capped at 1,200 characters because a URL is
about 2,000 and percent-encoding eats the rest; the book does not travel in the link, the connector
fetches it. Without a connector it is still a real conversation about a real book — the reader just
carries the outcome back by hand.

Verified live, not only in tests: the whole loop through the actual stdio MCP server against a
running API — 14 tools listed, insight written, chapter title resolved on read-back, book-level entry
first, both-identifiers refused, another user seeing nothing. 1,533 unit + 20 MCP-wire + 771 web
tests green; 13 new integration tests against the live API.

**Second pass over the gaps that shipped with it.** Four of the five things flagged as open turned
out to be worth acting on, and checking them corrected two of my own claims.

*The write ceiling.* `save_my_highlight` had a per-call limit and nothing else, so a client told to
mark what matters could mark a book to illegibility. Now `HighlightsEndpoints` caps a book at **200
assistant-placed highlights**, counted by `anchor_json->>'source' = 'mcp'` — the field the bridge
already writes — so a person highlighting heavily is never counted, including on a book an assistant
has also marked. Verified by seeding 200 rows: the 201st is refused, a human anchor on the same book
still saves. The first attempt used `.Contains()`, which EF compiles to `LIKE`; `anchor_json` is
jsonb and Postgres refuses `LIKE` against it outright, so that would have thrown on the first write
past the gate. Reading the field is also independent of whitespace and key order, which a substring
match is not, and a drift test now asserts both sides agree — the two live in different projects with
an opaque column between them, and a cap that silently stops matching is the worst way for a limit to
fail.

`POST /me/highlights` also gains a rate limit, and it is the **only policy in the codebase partitioned
by user id rather than IP**. The endpoint is reached both by a person in the reader and by the MCP
bridge, which talks to the API over the internal docker network — so every assistant write in the
deployment arrives from one container address, and an IP key would let one looping client throttle
every other MCP user. Verified: user A throttled after 116 writes in a window, user B from the same
IP in the same second still served.

*"Not your book" versus "nothing here."* `GET /me/insights` filtered by `user_id` and so leaked
nothing, but answered a stranger's book with `[]` — and an empty list is a truthful answer to "what
have I worked out about this book", which lets a wrong id read as a fact. It checks the book first
now, like `GET /me/highlights/userbook/{id}` does, and the bridge distinguishes the two.

*A claim of mine that was wrong.* I reported that `save_my_highlight` could not reach a chapterless
PDF upload. Production says otherwise: the two books with no chapters are **failed ingests**, not
chapterless PDFs, and every readable book has chapters. But checking it found the real version of the
problem, which is worse and affects **half the library** — 36 of 75 uploads are PDFs, the reader shows
a PDF as the original document (ADR-012), and `PdfHighlightLayer` only paints `kind:"pdf"` anchors.
A text-anchored highlight from MCP is therefore saved, listed, and shown on the Highlights page, but
never drawn over the page. `get_my_book` now reports `rendersAsOriginalPdf` and the tool description
says what happens, so the model can tell you rather than leaving you hunting for a mark that was never
going to appear.

*And one that was understated.* I called `chapter_number` "0-based for editions, 1-based for user
chapters". It is neither: production has every edition starting at 0 but **four uploaded books
starting at 2**, and locally five editions start at 1. It is an ordering key that was never a display
ordinal, `BookDetailPage` renders `chapterNumber + 1` and `UserBookDetailPage` renders it raw, and
both are wrong for the exceptions. Written down in `CLAUDE.md` rather than papered over with a
migration nobody asked for.

**And then the feature was pointed at a real uploaded book, which is when it broke.** Everything up
to this point was exercised against canned JSON and a catalog book, because the local database had no
uploads. Clipping an article to make one turned `search_my_library` up empty on a book that plainly
contained the search term.

`GET /me/library/search` was answering **500 on every call, and always had been.** Its raw SQL aliases
its columns in PascalCase, the context is built with `UseSnakeCaseNamingConvention`, and that
convention applies to the `SqlQueryRaw` row type too — so EF asked for `chapter_slug`, was handed
`"ChapterSlug"`, and threw before reading a row. Nobody had noticed because the only caller is the web
Library page's search box, which renders an empty result on failure: a library search that finds
nothing looks exactly like a library search that failed. So the colleague's bug report was righter
than it knew — the endpoint their spec called step 1, and called done, has never returned a result.
Aliases are snake_case now, both SQL branches, with an integration test that asserts a 200, because
only real SQL against a real database can catch it.

The bridge was making it worse in its own way: `SearchMyLibraryAsync` mapped any non-2xx to an empty
list, so a 500 reached the model as "you have no books about this" — the same confident-and-wrong
answer this work fixed twice elsewhere and left standing here. Failure and emptiness are separate
answers now.

Two smaller things the same run found. `list_my_book_highlights` reported `chapterId: null` for every
highlight on an upload, because an upload's chapter lives in `userChapterId` — so a model could not
tell what it had marked where, which is most of the point of listing them before marking more. And
`get_my_book` is where `rendersAsOriginalPdf` had to go, since that is the call a model makes before
writing anything.

*The one left alone.* The integration suite trips its own rate limits locally, because CI raises
`CLIP_PERMIT_LIMIT` and friends and a developer's `.env` does not. Putting the raised values in
`.env.example` would weaken production for anyone who copies it, so `CLAUDE.md` now carries the
command instead — along with the sharper trap: the windows are minutes long, so re-running a suite to
confirm a failure is what causes the next one.

**Deliberately not in this work:** semantic retrieval and the indexing tools (they matter for 3 books
until indexing is decided); bulk indexing, whose cost is not embeddings — a quarter of a cent per
book — but the PDF vision parse at $0.00586 a page; the fate of our own Book Chat, which is a focus
decision and should not be smuggled inside a bug fix.

## Docs — ADR-015, and the scenario that was never in QA-001 — docs — 2026-09-07

The record for the position work, and the reason it took sixteen commits to get here.

**[ADR-015](../01-architecture/adr/ADR-015-reader-position-is-logical.md)** states the model and,
more usefully, states what was already decided and not done: ADR-007 chose a logical position in
January 2026 and listed `scrollY` among the things explicitly not used; `scroll:<slug>:<pixelOffset>`
shipped four months later. ADR-007 now says so, pointing forward. ADR-013 records that its rules are
unchanged and still govern the locator — rule 3 is precisely *why* the position became a column
rather than a third space.

**QA-001 never crossed a chapter boundary.** Its four steps navigate by TOC and by the library card,
and both of those stay inside the chapter the URL names. The mobile reader appends the next chapter
into the same document as you scroll, which is where every reported "it forgot where I was" has
lived — so the suite passed for eight months while readers lost their place. Five steps added,
marked UNTESTED because they are: read across a boundary and change the font size, then kill the
app, then the same offline, then cross-device and against an old build, then a PDF in Original
layout to confirm it is untouched.

**One thing was declined rather than built.** Making the route follow the reader would remove the
URL/document disagreement at source, and while the position was a pixel that disagreement caused
data loss. It no longer can: an anchor names its own chapter, so a position cannot be applied to the
wrong one — `resolveTextPosition` returns null and the caller changes route instead. What remained
was cosmetics on a client with no address bar, against surgery on the reset key of
`useReaderPersistence` and the identity of the WebView document, which is where all four of #496,
#500, #501 and the font-size defect lived. `readerWriteTarget.test.ts` pins the property the surgery
would have made structural, so if the reasoning stops holding, a test says so.

<a id="2026-09-07-library-the-shelf-that-could-not-continue"></a>

## Library — the shelf that could not continue — backend, shared — 2026-09-07

Slice 6, and the smallest change with the longest history.

`LibraryShelvesService` has always SELECTED the progress row's locator —
`CurrentLocator = latestProgress.Locator` — and then thrown it away, because `LibraryShelfItemDto`
had nowhere to put it. So the shelf named "Continue Reading" could show how far into a book a reader
was and structurally could not offer to continue from there; the client had to make a second request
per book to find out. `GET /me/books` had the same hole: a percentage and a chapter slug, no
position.

Both DTOs now carry the locator and the logical position. `rankContinueReading` exists because of
exactly this gap — its docstring says so — and can now be given the whole answer rather than
reassembling it.

While there: `pickUserBook` was the last place still reading a chapter slug without consulting the
locator beside it. It has not cost anything yet, because that slug is client-written rather than
server-derived — but one branch of one function obeying a rule the other branch does not is how
#496 became #500 became #501, and the comment above it now says which rule and why.

<a id="2026-09-07-reader-web-joins-the-position-model"></a>

## Reader — web joins the position model, and stops splitting on colons — web — 2026-09-07

Slice 4. The same model on the other client, plus two defects found by looking.

**Web had the same disease without the amplifier.** It renders one chapter per route and applies
typography as inline styles on the `<article>` — no remount, no reload, nothing to lose. So the text
simply re-wrapped under a fixed `scrollTop`, the reader moved, and the debounced save then wrote
where they had been moved to. Nothing in `useReaderScrollSync` has ever depended on `settings`; that
absence *was* the defect. It now captures the reading line before the reflow and re-applies it after
— signalled by a `ResizeObserver` on the article, because a style change fires no `resize` on window
— and re-primes the skip window so the transient is never saved.

**`locator.split(':')`.** Web parsed the locator inline while `parseScrollLocator` sat in
`@textstack/shared` being used only by mobile. The shared one reads from the RIGHT precisely because
a chapter slug is derived from a user-supplied title: `scroll:act-i:scene-ii:900` gave web a slug of
`act-i` and `parseInt('scene-ii')` → NaN → offset 0. Two implementations of one format, one of them
wrong, which is the thing `@textstack/shared` exists to prevent. There is a test for the colon now.

**The keepalive write sent no `percentUnit`.** `flushSave` builds its body by hand rather than going
through `upsertProgress`, which adds the declaration for every other writer — so the LAST write
before a tab closes, the one most likely to be the newest the server ever sees, silently failed to
store its percentage (`ProgressUnit` drops an undeclared one). The comment on the user-book twin says
this is "exactly how it came to be missing one of them"; the catalog twin had it too.

**Also smaller.** The three copies of the save — save-on-open, the debounced scroll save, the
keepalive flush — each built the locator itself and each branched on mode. They are one `writeProgress`
now, which is why threading the text position through cost one call site rather than three.

The e2e that has never existed exists — and cost two wrong assumptions before it did. It first
assumed a chapter long enough to scroll; CI seeds a single short paragraph. It then assumed the
saved anchor comes back byte-identical after a reflow; it does not, and should not — the reading
line falls on a different character of the same passage. It asserts what a reader actually depends
on: a position is still saved, it still names this chapter, and the passage it quotes is still in
the text. That fails if the save writes null, another chapter, or an anchor pointing at nothing.

**And the short chapter was not just a bad fixture — it was a defect.** The reading line is a
quarter down the viewport, so a chapter that ends above it — a poem, a preface, a clip, the stub
last chapter of a book — yielded no caret, no anchor, and silently no logical position at all,
falling back to the pixel offset forever. Measured in a browser: a one-paragraph chapter ends at
108px with the line at 200px. The probe is now clamped into the chapter's own visible band, on both
clients.

<a id="2026-09-07-reader-the-position-is-a-place-in-the-text"></a>

## Reader — the position is a place in the text — mobile, backend, shared — 2026-09-07

Slices 2 and 3 of the reading-position work. Slice 1 stopped a font change destroying the reader's
place; this is the model that stops a pixel being the answer at all.

**What a position is now.** `TextPosition` in `@textstack/shared`: a chapter slug, a text anchor
(30 characters of context either side of a 64-character quote), a character-offset hint and a
chapter fraction. Which is to say: a highlight without a colour. The resolver is the one highlights
have used since it was written — `findAnchorOffset`, whose own docstring names this case: *"A
highlight, a bookmark **or a reading position** cannot be stored as a pixel offset or a character
index."*

**Why not `paragraph_index`, which is what ADR-007 proposed.** The reason is specific rather than
general, and worth stating: the index of a `<p>` within a chapter survives a font change perfectly
well — it is a DOM fact, not a text fact. What it does not survive is re-ingestion, which deletes
and recreates every chapter from freshly parsed HTML, and the two clients sanitising differently. A
text anchor survives both.

**Why a column and not a third locator space.** `text:<slug>:<offset>` was the obvious shape and it
is a trap. ADR-013 rule 3 — *same space, accept, declared or not* — is the entire compatibility
story for already-installed builds. Introduce a third space and the first new client to write it
turns every old client's `scroll:` write into an undeclared cross-space write, refused by rule 5: a
phone that updated would silently stop a desktop that had not from saving anything. On the catalog
path, which `MayReplace` does not guard at all, it is worse — the old client's write lands, and the
old client cannot parse what it overwrote. So the position went into `reading_progresses.position_json`
and `user_books.progress_position_json`, beside a locator that is still written in the old form.
`LocatorSpaceTests` now asserts that `Derive("text:…")` is *still null*, so the trap cannot be walked
into later by someone who does not know it is one.

**One invariant, and it is the whole server-side job:** a row never holds two positions that
disagree. A write carrying no position CLEARS the stored one — not "keeps what was there", because
an old build writes the locator alone and its pixel offset is then the only true statement on the
row. A `page:` write clears it (a PDF's page *is* its logical position). A refused write changes
nothing. An oversized one drops only the position. Same rule on both paths, one function,
`ReaderPosition.ToStore`.

**In the WebView.** The position rides along with the existing `progress` message rather than
costing a round trip, because `saveProgress` is called from an unmount and from an AppState listener
and cannot wait for an answer. The extraction excludes vocab overlays and inline translations — they
are DOM nodes the reader never wrote, and counting them would shift every offset the moment a word
was saved — and caches per chapter element, so it costs one walk rather than one per scroll.

Two things had to be fixed to make it possible. `window.__TSAnchor` was installed only by the
overlay bundle, which is emitted only when the overlay-v2 flag is on, so with the flag off the
resolver degraded to a bare `indexOf` — no context ladder, no offset verification, no fuzzy
fallback. Survivable for highlights, which have a legacy path; not survivable for a position
resolved from an anchor on every chapter open. The resolver now has a 3.6KB bundle of its own that
is always inlined, and the overlay flag keeps meaning what it means. And the mobile document had no
chapter elements at all, so an anchor could not be scoped to a chapter the way web's already was;
slice 1's `[data-chapter-slug]` wrappers are what made this possible.

**Verified in a real browser, which is the only place it means anything.** Capture at 62% of a
chapter rendered at 18px/1.65/left; rebuild the document from scratch at 25px/2.0/justified; restore
from the anchor. Same paragraph. The scroll position moved from 5686 to 11951 — the pixel was never
the answer.

Also here: the two mobile bundles now share one definition with their CI drift guard, which had
been carrying its own copy of the banner text — a drift guard that could itself drift.

Behind a per-device flag (`textstack.readerTextPosition`), on by default. Only the READ is gated;
the write never is, so a device switched off keeps accumulating positions for when it is switched
back, and switching off falls back to exactly the old pixel behaviour with nothing lost.

<a id="2026-09-07-reader-a-font-size-change-stops-destroying-your-place"></a>

## Reader — a font size change stops destroying your place — mobile — 2026-09-07

Slice 1 of the reading-position work. Reported for at least the third time, patched sixteen, and
never once at the level it was actually broken.

**The report.** Read into chapter two, close the app, come back — and you are in the middle of
chapter one.

**The mechanism.** The mobile reader appends chapters into the SAME document as you scroll; the URL
never moves off the chapter you opened. `ReaderShell` keyed its document on typography, so changing
a font size rebuilt the WebView — and a rebuilt document is built from the ROUTE chapter, which is
chapter one. `useReaderPersistence.onWebViewLoaded` then re-applied `progressRef` — your fraction of
chapter TWO — as a percent of that document. The write gate was already open for the route chapter,
so two seconds later the debounce wrote it. Measured on the shipped code: 55% of chapter two became
74% of chapter one and `scroll:ch-1:1636` replaced `scroll:ch-2:1200`, locally and on the server.
Unrecoverably: a pixel offset cannot be un-overwritten.

**The level it was broken at.** [ADR-007](../01-architecture/adr/ADR-007-reader-autosave.md),
accepted 2026-01-19, decided the position is *a logical position in the text* and listed `scrollY`
among the things "explicitly not used". Its acceptance criteria include "Font changes do not break
progress". On 2026-05-17, `30698d5e` — *"autosave + restore **pixel-accurate** scroll position"* —
introduced `scroll:<slug>:<offset>`. Everything since has defended pixels. No test anywhere asserted
that criterion; there is now one, and it is named after what it costs.

**What changed.** Typography left `readerDocumentKey` and is injected into the live document
instead, the way padding and colour already were since #467 — so the common case has no rebuild at
all, and the chapters infinite scroll appended are no longer thrown away and re-fetched. The
rebuilds that remain (`overlayV2`, OpenDyslexic's inlined `@font-face`, a re-parsed chapter) are told
to the persistence hook *before* the new document loads, because the fresh document's load event is
what overwrites the one fact that decides what to do: which chapter the reader was actually in. If
that is not the route chapter, the route now goes and gets it rather than restoring into the wrong
one.

**Three defects found on the way, each its own data loss.**

`registerChapter` sampled a chapter's `top` once, when it was appended, and never recomputed it.
That was invisible only because nothing reflowed a live document — and moving typography to
injection would have made every stored top a lie, `currentChapterBounds` name the wrong chapter, and
`reportProgress` post that wrong slug. The same corruption by a different route. Tops are now read
from the elements, which now exist: each chapter is wrapped in `[data-chapter-slug]`, the mobile
equivalent of the `data-chapter-id` web has had all along.

`__textstackRestorePercent` multiplied a CHAPTER fraction by the whole DOCUMENT's `scrollHeight` and
never subtracted the viewport. Even with one chapter loaded it landed roughly `innerHeight × fraction`
too deep, and at ~1 it clamped to the bottom. Restoring by percent was never a safe fallback.

And the one only a browser could find. The document sets `html { scroll-behavior: smooth }`, so
every restore was an *animated* scroll: `window.scrollY` still read the old position on the next
line, so the acknowledgement that opens the write gate reported a place the reader was not at yet —
and the animation went on firing `reportProgress` with intermediate positions after the gate had
opened. A restore to 28793 acknowledged 15042. Restores now jump.

**Verified** on the real document in a real browser, with real layout: read to 55% of chapter two,
change 18px/1.65 to 24px/1.9 justified, and the same paragraph stays under the reading line at the
same fraction of the same chapter. The unit tests run the extracted WebView functions against a
fake layout — jsdom has none — and each one fails if its fix is removed.

Deliberately not yet: the logical position itself. Slice 1 re-anchors by chapter-scoped ratio, which
survives a reflow but not a re-parse and not a different device. The text anchor that `textAnchor.ts`
has been resolving for highlights since it was written — its own docstring says "a highlight, a
bookmark **or a reading position** cannot be stored as a pixel offset" — is slice 3.

<a id="2026-09-06-vocabulary-blitz-runs-blitz-and-four-smaller-things-a-qa"></a>

## Vocabulary — Blitz runs Blitz, and four smaller things a QA pass found — mobile — 2026-09-06

`aca11d9c` (#562), closing #558 and #559 from the QA-005 run.

**#558 was not a race. It failed every time.** `app/vocabulary/review.tsx` had two mount effects.
The first dispatched `setReviewMode('blitz')` from the route param. The second called
`startSession(batchSize, review.reviewMode, …)` — and `review.reviewMode` there is the
mount-render closure value, still the hook default `'classic'`. `startSession` dispatches the mode
it is handed. Two dispatches, one React batch, the later one wins. The comment sitting above that
call asserted the opposite of what happened.

So **Blitz was unreachable from the entry point entirely** — including from `ClusterBonusCard`,
which hard-codes `reviewMode=blitz` in the URL it pushes. It worked only from the end-of-session
toggle, a separate event in a separate render, which is exactly how a mode nobody could select
survived to production looking selectable: the sheet showed Blitz checked, and remembered it.

Web has always done this correctly (`apps/web/src/pages/VocabularyReviewPage.tsx`): derive the
starting mode from the params as a **plain value** and hand that value to `startSession`, never
reading hook state during startup. One writer, no batch to lose. The same rule now lives in
`apps/mobile/src/lib/reviewMode.ts` — extracted to `src/lib` rather than left in the screen because
mobile's `vitest.config.ts` collects only that directory. **A rule that lives in a screen is a rule
that cannot be tested, which is how this shipped.** `reviewModeFromParam` is total and deliberately
case-sensitive: `?reviewMode=Blitz` is a caller bug, and silently repairing it hides the caller.

The choice also did not survive a cold start. It lived in `useState`, so "it persists across
reopening the sheet" only ever meant "the tab stayed mounted"; killing the app reverted to
Flashcards. It is now in AsyncStorage under `vocab.reviewMode.v1`, matching what web keeps in
`localStorage['practiceMode']`, and a storage failure falls back to the default rather than breaking
a screen.

Worth stating because the names collide: this choice is `ReviewMode = 'blitz' | 'classic'`, a
**client** concept. The server's `ReviewCardDto.reviewMode` is unrelated, is read by no client, and
is documented as vestigial on the field itself in `packages/shared/src/types/api.ts`.

**#559, fixed second on purpose.** `ReviewFeedback` ran a dictionary lookup for every card without a
stored definition, then — in `classic` mode — returned the *mini* feedback branch, which has no
definition slot. The fetched value is only ever read in the blitz layout. QA measured two lookups
fired and discarded per session, ~3 s each against the dictionary upstream that was down that day.
The ordering was deliberate: until Blitz was reachable, the branch that *can* show a definition could
not be verified at all, so fixing #559 first would have meant shipping an unobserved fix.

**Three pieces of friction on the guest→account path**, all on work that shipped a week earlier:

- **"Create free account" opened the auth screen on the *Sign in* tab.** The screen read no route
  params at all. It now takes an optional `mode` param as a `useState` **initializer**, not a syncing
  effect — a sync would yank a user back to Register after they deliberately tapped Sign in. The
  other twelve callers pass nothing and still land on Sign in.
- **"Password must be at least 8 characters" stayed red at 14 characters.** The validation was
  correct; `setError('')` only ran on the next submit and `onChangeText` cleared nothing. The same
  defect was in `reset-password.tsx`, which is the screen a user meets straight after a reset email.
- **A guest's Profile advertised "Upload space 0 B / 50.0 MB"** for a capability guests do not have.
  `profile.tsx` destructured four capabilities from the tier and not `canUpload` — the one governing
  that row was the one the screen never read.

<a id="2026-09-06-mobile-one-word-tap-buys-one-translation-not-two-and-the"></a>

## Mobile — one word tap buys one translation, not two, and the screen behind the reader stops refetching — mobile — 2026-09-06

`37758fa9` (#561). Four kinds of wasted request, found by running QA-005 through a logging proxy.
One of them spends money on the most frequent action in the product.

**`translateCache` memoized the result and never the promise.** Two callers inside one round trip
both read `cache.get(k) === undefined`, both called `/translate`, and both were billed — that is
OpenAI `gpt-4.1-nano`, twice per word tap. The file's own docblock claimed it "de-dupes the double
translate per tap"; it could not, because there was no in-flight map. The server-side file cache does
not save you either: the second request reads an entry the first has not written yet.

The fix is a `Map` of keys over `createSingleFlight` rather than a second promise tracker.
`createSingleFlight` already does the one job needed here — N callers, one call, everyone gets the
same promise, slot released on **both** settlements — and it is the version of that rule this repo
already has tests for. A hand-rolled tracker would have meant getting the release-on-reject path
right a second time, in a file that had already lied about doing it once. Slots are evicted on
settle, so the map never outgrows the words actually in flight.

`TranslationSheet` bypassed the cache outright, so every Translate press re-bought a gloss the
toolbar was already holding in memory.

**`GET /books/{slug}` fired twice on reader open, and that one is ours** — a regression from the
guest work (#554). `ReaderSessionGate` mints a guest, `isAuthenticated` flips false→true *globally*,
and the book detail screen still mounted underneath refetches at the instant the gate mounts the
reader. `readerSessionGate.ts` documents freezing that flag for the reader's lifetime; nothing froze
it for the screens behind. The effect is now split: the public fetch keys on the slug, the
session-dependent follow-ups (library membership, progress) key on the session.

The split cost more than a dependency change. `setLoading(false)` used to run after
library + progress, so one skeleton covered both round trips; splitting naively paints the hero one
RTT early and an in-progress book flashes "Start Reading" before its progress lands. `loading` is now
derived from a one-way `sessionLoading` latch — seeded `true` for an account so nothing changes,
`false` for a guest so the book paints at once and a mid-flight mint refreshes without throwing up a
skeleton.

**`AddToCollectionSheet` was mounted unconditionally on four screens.** A `<Modal visible={false}>`
draws nothing, which reads like it costs nothing; the component around it mounts with its parent and
its hooks run immediately, so `useCollections` fired `GET /me/library/collections` on every open.
`useCollections` caches successes only, so on the public book-detail screen — reachable signed out —
that is a **401 on every single open, forever**, and it drags `authFetch` into
`handleTerminalAuthFailure()` on a screen that never needed a session. Two of the four screens were
not in the QA report: fixing only the reported one would have changed nothing observable, because the
60 s module cache would have served the neighbour's request instead. `useSheetMount` latches rather
than unmounting on close, so the slide-out animation the sheet was written for still runs.

**Book detail kept its pre-reader progress** — "Start Reading" with no progress row immediately after
leaving the reader, correct on the next visit. The file already imported `useFocusEffect` and
`useCallback` and used neither: the refetch was planned and never written. Same fix as the one
already made on `my-books/[id].tsx` for the same symptom.

**Not done, deliberately.** The reader bridge dispatches the tap and Android's own `selectionchange`
as two messages whose exact-match dedupe fails when they differ by one character. The single-flight
above makes every *same-key* duplicate free but not that pair, since different text means different
keys. The likely cause is `WORD_RE` carrying a straight apostrophe while the extraction pipeline
writes curly ones — but the guard that looks obvious re-breaks drag-to-extend, fixed directly above
it and verified on a device. Measure both dispatched strings first, then fix the confirmed
difference.

## QA — the guest loop, walked on a device with a traffic log — docs — 2026-09-06

<a id="2026-09-06-dictionary-an-upstream-outage-stops-being-an-outage"></a>

## Dictionary — an upstream outage stops being an outage — backend — 2026-09-06

`api.dictionaryapi.dev` went down on 2026-09-05 — a direct probe returned Cloudflare 522 after
19.6 s. `GET /dictionary/en/serendipity` faithfully turned that into **504 after 10.09 s**, three
times out of three. The upstream outage was not ours. What was ours: a word tap in the reader
waited ten seconds and then got an error, with nothing to fall back on, because there was no
server-side cache of any kind.

**The cache is the fix.** A SHA256 file cache in front of the proxy, same shape as `ExplainCache`
(hex key, one JSON file per entry, best-effort IO that degrades to "no cache" rather than failing
the request), with one deliberate difference that everything else rests on: **the reader does not
drop expired entries**. `ExplainCache` returns null past its TTL; `DictionaryCache` returns the
entry with its age, and the policy decides. That is what makes the load-bearing rule expressible —
*on upstream failure, serve a stale entry rather than an error*. A definition from last month is
correct. A 504 is not. There is no upper bound on how stale a fallback may be, because the
alternative to a three-year-old definition is no definition.

Definitions are effectively immutable, so freshness is 30 days. "No such word" is not: it is a
claim about coverage, and dictionaries gain words, so **negative entries expire in 24 hours**. They
exist so a typo does not send a request to a dead service every time it is tapped — during the
outage a cached negative answers in 14 ms without leaving the box.

Keys normalize `(lang, word)`: `Book`, `BOOK` and `  book  ` are one entry. Hit rate is what makes
the fallback work at all, so the normalization is part of the contract rather than an optimization —
a reader tapping a capitalized word at the start of a sentence must reuse the lowercase entry. The
key is length-prefixed (`2:en:book`), because both halves come off URL segments and a plain
`lang|word` join lets `("en", "us|book")` and `("en|us", "book")` hash to the same file.

**The timeout was wrong for the interaction.** 10 s is a budget for a batch job; this is a gesture.
`Dictionary:TimeoutSeconds` is **3** — enough for a cold DNS + TLS handshake to the upstream CDN on
a mobile network plus a slow-but-alive query, and under the point where a tap reads as broken.
During the outage the old budget bought nothing except ten seconds of spinner before the same error.

**Failure is now honest and distinguishable.** Three outcomes, and a client can tell them apart:
`200` with `cached`/`stale` flags, `404 {code: "not_found"}` — upstream answered, this word has no
definition — and `503 {code: "dictionary_unavailable"}` — we could not ask and had nothing cached.
The old 502/503/504 split gave clients three different ways to say one sentence; a reader UI cannot
act on the difference between a timeout and a connection refusal, so both are logged and both
collapse to 503. `X-Dictionary-Cache: hit|stale|negative|miss` carries the operator half.

**No LLM fallback**, deliberately. `/dictionary` is one of three routes (with `/translate` and
`/api/tts`) kept anonymous because the reading loop depends on them. Routing misses to
`ILlmService` would put paid inference behind an unauthenticated URL — reopening from the other side
exactly the hole `RequireAiAccount` closes.

The policy is pure functions over a cache entry, so the rules that matter are unit-tested without a
network: stale-on-failure, the TTL boundary, the shorter negative expiry, clock skew, corrupt and
payload-less files, and key normalization. Verified against the live stack while the upstream was
still returning 522: cold cache 503 in 3.01 s, fresh entry 200 in 8 ms with no upstream call at all,
and a 90-day-old entry served as `200 … "stale": true` after the 3 s probe failed.

The one honest cost: while upstream is down, a *stale* entry still pays the 3 s probe on every tap
before falling back. Fresh entries — anything looked up in the last 30 days, which is most of them
during any plausible outage — cost nothing. A short-lived "upstream is failing, skip the probe"
breaker would close that tail and is not built.

<a id="2026-09-06-guest-the-whole-loop-without-an-account"></a>

## Guest — the whole loop without an account — mobile, backend — 2026-09-06

Mobile mints an anonymous **guest session** on demand, so a reader completes the loop the product is
built around — read, tap a word, save it, see it in Vocabulary, review it — with no account.
Registering promotes that same server row **in place**; signing in to an existing account merges it.

The backend half already existed. Web used it. Nothing under `apps/mobile` had ever called
`POST /auth/guest`.

The mint trigger is deliberately narrow: **opening a book**, and nothing else. Web mints from three
places (reader mount, upload, the third pending vocabulary word); mobile mints from one, through
`ReaderSessionGate`, which holds a themed blank until the session question is *settled* rather than
firing the call and letting the answer arrive mid-mount. That is not caution for its own sake —
`isAuthenticated` is a fetch input all through the reader (`useReaderBook` has it in the dependency
array of the effect that loads the book, `useEditionReaderSource` re-creates `loadPosition` on it),
so a session landing 400 ms after mount reruns the whole load underneath a reader that has already
restored the scroll position. Held constant for the reader's lifetime, that race cannot happen.

The gate can never hide the book. Every failure — mint rejected, rate limited, offline, bootstrap
wedged, 3 s deadline blown — resolves to *render*. Reading works from the chapter cache and a session
is an enhancement, not a precondition.

The posture, the capability table, and the alternatives rejected are recorded separately in
[ADR-014](../01-architecture/adr/ADR-014-guest-sessions.md). This is what it took to make it safe.

### Two ways this used to destroy data

**`mobilePost` never sent `Authorization`.** Every mobile sign-up and sign-in went out without a
bearer, so the server's guest resolution returned null, `MergeGuestAsync` never ran, and a guest who
registered lost every word, highlight, bookmark, note, session and page. Not an edge case — the
only case.

The interesting part is how thin the proof was until it wasn't. The fix is one header. What makes it
a guarded fix is the mutation: strip the header from `mobilePost` and **four** tests in
`packages/shared/src/api/auth.test.ts` go red, one per merge entry point (`/auth/register`,
`/auth/login`, `/auth/google`, `/auth/apple`). Reading the token also cannot break sign-in — a
keychain that throws is caught and the call proceeds bearer-less, because "we could not read your old
guest token" must never become "you cannot sign in".

While reading that path, a second copy of the same parse turned up: `GetGuestUserId` did a global
`.Replace("Bearer ", "")` while `GetUserId` matched the scheme case-insensitively. A client sending
lowercase `bearer` therefore authenticated *and* was silently not merged, and the `.Replace` would
also cut the literal string out of the middle of a token. There is one reader now
(`ClaimsPrincipalExtensions.GetAccessToken`), so the two cannot disagree again.

**Profile offered a guest a plain Sign Out.** Three SecureStore keys are the only handle that exists
on a guest account: the email is synthesized, there is no password, and no one — not the reader, not
support, not us — can ever reach the row again once they are gone. The row itself survives:
`GuestCleanupWorker` explicitly refuses to prune a guest holding vocabulary, highlights, bookmarks,
library rows, uploads, notes or progress. So the books stay on the server forever and are
permanently unreachable.

That is a delete, and it shipped as an unconfirmed row in a settings list, one tap from the Profile
tab, styled like every other harmless action. It is now behind a destructive confirm that names the
loss in words rather than asking "are you sure", and the branch is a pure function
(`signOutIntent`, `src/lib/profileActions.ts`) so it is asserted rather than eyeballed.

### The bug that was invisible by construction

Access tokens live 60 minutes. Nothing on mobile refreshes proactively — `onUnauthorized` only fires
when some *other* call takes a 401, and the once-per-session profile refetch is skipped for guests.
So the ordinary path, read on Monday and tap "Create free account" on Tuesday, arrives at
`/auth/register` holding a dead token.

On the merge entry points an expired bearer is not a 401. It is a **silent 200**: the server
validates with `ClockSkew = Zero`, gets nothing, never runs the merge, and answers success. From the
client's side a registration that kept everything and a registration that threw everything away are
byte-identical responses. An expired bearer is therefore strictly *worse* than none — none cannot
masquerade as a live guest.

Fixed from both ends, because either alone leaves a hole:

- **Client**: `isTokenExpiring` (`packages/shared/src/api/tokenExpiry.ts`) reads `exp` unvalidated —
  it is our own token and no trust decision rests on it — with a 60 s skew, and refreshes through the
  *existing* single-flight `onUnauthorized` rather than adding a second refresh loop. A token it
  cannot parse is reported as **not** expiring, which is the conservative direction: a refresh that
  fails offline returns null, and we would then drop a bearer that was in fact valid.
- **Server**: the classification now distinguishes *no credential* from *unusable credential*. The
  first is an ordinary registration and stays quiet; the second sets `guestMergeSkipped` on the auth
  response (`invalid_token` | `merge_conflict`) and logs one structured Warning carrying route,
  reason, token expiry and whether the client was mobile. Deliberately **not** a 401 — someone with a
  stale token in their pocket and no guest data at all must still be able to register. Sign-in
  proceeds; it is just no longer silent.

The client refresh closes the common case. It does not close a badly skewed device clock, a refresh
token already rotated, or a token read back corrupt from a damaged keychain — which is why the server
signal exists and why it is the part that counts occurrences. `guestMergeSkipped` is additive and
optional; **no client reads it yet**. The server stopped being silent before the app started
speaking, and that ordering is on purpose: the number is needed before the copy is worth writing.

### One unique index the merge did not know about

`MergeGuestAsync` bulk-updated `ReadingSessions` under a comment reading *"plain re-parent (no unique
conflict on UserId)"*. It carries two, both partial:

```
(user_id, edition_id,   started_at) WHERE edition_id   IS NOT NULL
(user_id, user_book_id, started_at) WHERE user_book_id IS NOT NULL
```

and `StartedAt` is **client-supplied**, accepted up to seven days old. It is the de-facto idempotency
key of the offline session queue. So "the guest and the account both hold a session with the same
key" is not a microsecond race — it is one queued session flushed under two identities, which is
exactly what happens when someone reads offline as a guest and then signs into an account that
already flushed the same stretch.

The failure mode is the worst shape available. 23505 → the whole merge transaction rolls back →
sign-in answers **500** → the client re-presents the same guest token on the next attempt → 500
again, forever. Unrecoverable without wiping app data, which destroys the guest session too. Fail-fast
here loses the data *and* locks the user out.

Two changes. A targeted DELETE mirroring the index predicate, then the bulk UPDATE — the account's
row wins, the guest's conflicting row is dropped, same rule as every other unique-keyed table. Not
routed through the existing `ReparentDropOnConflictAsync` helper on two counts: the helper compares
one composite key per row and would treat two rows that are both *outside* a partial index
(`edition_id` null on each) as colliding, silently dropping a session the database was happy to keep;
and `reading_sessions` is the one high-cardinality table in the merge, while the helper materializes
both sides into memory.

And a floor under the whole method: `MergeGuestAsync` now returns `bool` and catches SQLSTATE class
23 — and only that class. Constraint violations are deterministic; the offending row is still there
on the next attempt, so letting one escape turns a bad row into a permanent outage. Timeouts, dropped
connections and cancellation are deliberately *not* caught: those are the cases where failing is
correct, because the user retries and the merge runs again. Swallowing them would turn a recoverable
retry into permanent orphaning — the same trade, pointed the other way. The catch checks both
`DbUpdateException` and a bare `Npgsql.PostgresException`, because `ExecuteUpdateAsync` /
`ExecuteDeleteAsync` bypass the change tracker and never get wrapped; a `DbUpdateException`-only
catch would have missed the exact failure it was written for.

The merge grew in the same pass, and every addition is a table that would have been dropped on
sign-in: `PendingVocabularyWords` and `WordLookups` (same unique key as `VocabularyWords`, so
drop-on-conflict, not bulk re-parent), `WordClusters`, `Collections`, `UserVocabularySettings`
(copied, not re-parented — `(UserId, SiteId)` is its primary key), and the guest's `NativeLanguage`,
which they answered minutes ago on their first word tap and which nothing else carries.
`UserChapterChunk` is the one worth remembering: its `UserId` is denormalized off `UserBook` with no
FK to `User`, so those rows *outlive* the guest instead of cascading away, retrieval hard-filters on
`user_id`, and `RagStatus` still reads Ready — a silently dead "Ask this book" on a book the reader
can see in their library.

### A guest token was a free path to the model

Librarian, tutor, "Ask this book", book chat, study buddy and RAG indexing were account-only **in the
UI** and open on the wire. A guest session mints a perfectly valid bearer token, and every limiter
fronting those routes partitions on IP alone — so the client flag was an affordance that had been
mistaken for a boundary, and guest sessions are free and unlimited to mint.

`RequireAiAccount()` (`backend/src/Api/Extensions/AiAccountPolicy.cs`) is an endpoint filter applied
at eight registration points, three of which are route groups. It resolves the caller's tier and
refuses before the handler runs, and therefore before any token is spent. `GET /me/chat` is inside
its group specifically because it **upserts on read** — it can INSERT the conversation row that only
exists to hold LLM turns.

It returns **403 `account_required`**, not 401, and the distinction is the point: one means *sign
in*, the other means *sign **up***, and they are different screens. Translate, dictionary and TTS are
deliberately untouched — they are anonymous endpoints and the reading loop depends on them.

The decision itself is not in the filter. It is `Entitlements:Tiers:Guest:AiEnabled: false` in
config, resolved through `IEntitlementResolver`; the filter is only the enforcement point. Unset
means *allowed*, on purpose — a mistyped key then costs a call on the OpenAI bill, rather than
silently killing AI for every paying user.

Saving vocabulary stays open but is metered: `DailyEnrichmentCap: 50` for the Guest tier, because
each new word queues distractor + hint + explanation generation. It clamps the user's own daily cap
rather than adding a second counter — enrichment is queued exactly where a word gains `ActivatedAt`,
so "new SRS activations today" already *is* "enrichment calls today".

### Three more, found on the way

**`PromoteLookup` bypassed the tier cap** exactly as `PromotePending` used to. "Add anyway" is
allowed to override the user's *own* daily pacing — they explicitly asked for that word — but not the
platform's LLM spend. Without the check, a guest parks rare words in lookups all day (that branch of
`SaveWord` returns before the cap check, because a lookup row costs nothing) and promotes them one at
a time up to the 5000-word ceiling: 100× the tier's daily allowance through the one door nobody was
watching.

**`updateUser` could resurrect a dead session.** It was the one queued writer that did not consult
the session epoch, so the once-per-session profile refetch could rewrite the `user` key *after*
`signOut()` had deleted all three — leaving a user with no tokens, which the mint decision reads as
"session exists" forever. Result: no new mint, every request 401-loops, and the only fix is
reinstalling. Two guards now (`writeUserIfCurrent`), because the epoch alone is not enough: if
`signOut()` bumps *before* the write is called, the write captures the already-bumped epoch and
compares equal. The second guard is the invariant itself — never write `user` when there is no access
token — checked inside the exclusive block where nothing else can be mid-write. Reachable from
ordinary use, not just a constructed race: `NativeLanguageContext.setNativeLanguage` goes through the
same path.

**`IntegrationSkip` counted 500 as "environment unavailable".** Which made every guard built on it
self-disarming: an endpoint that started throwing turned its own tests green by skipping them. It
cost this suite the guest-merge 500 above — the merge tests all sit behind that call, so a broken
merge reported as *skipped* rather than *failed*. 404 still skips (the endpoint is not deployed;
there is nothing to assert). 500 now fails, because the endpoint is deployed and threw, and that is
the defect rather than the environment. A suite that only appears to guard something is worse than no
suite, because it is believed.

### What was ruled out

**A pending-vocabulary queue on mobile.** Web keeps unsaved words in IndexedDB and replays them at
sign-up. Mobile does not need one any more — the whole reason it existed was that a signed-out reader
had nowhere to save. A guest is a real server row; the word goes to the server on the tap, like an
account's does. Building the queue would have been work thrown away by this same change.

**A bare `isGuest` boolean on the auth context.** Mobile's `isAuthenticated` is `user !== null` and
~70 sites read it; a guest flips all of them at once. But ~16 mean *"do I have a token"* — correct
for a guest, who **is** a real server row that syncs — and only ~8 mean *"is this a real account"*. A
flag forces every screen to re-derive `isAuthenticated && !user?.isGuest` inline, and the
re-derivation is where it goes wrong. The live example was on one screen: `profile.tsx` hid the edit
pencil behind `!isGuest` while the `TouchableOpacity` wrapping it still called `startEdit`, and
`pickAvatar` beside it had no guard at all — so a guest could `PUT /me/profile` on a throwaway row.
The policy was written twice in one file and one copy was wrong.

So `isAuthenticated` keeps its meaning and a pure `capabilitiesFor(user)`
(`apps/mobile/src/lib/capabilities.ts`, landed with no call sites in #553) owns the account policy.
A capability name says what the caller may *do* (`canEditIdentity`), so a reviewer can see it is on
the wrong control; `!isGuest` says only what the viewer *is*, and reads plausible next to anything.
`capabilityLiterals.test.ts` greps the source and fails the build on the re-derivation, with a short
allow-list where each entry carries its reason on the line.

One place the obvious migration would have been wrong: the root redirect keys on `isAccount`, not
`hasSession`. A guest holds tokens, so migrating it to "has session" would land every first launch on
an empty Library — a blank screen for exactly the reader who has chosen nothing yet. Discover is the
only front door with anything in it. The accepted cost is that a returning guest with saved books
still lands on Discover and taps Library.

### What is not covered

`apps/mobile` has **no component or hook test lane**, and its Playwright suite is excluded from both
CI and `tsc`. Every decision in this change is therefore a pure function under `src/lib/` — the only
mobile layer Vitest collects — and the ones that matter discriminate against the pre-change code
rather than restating it. But nothing executable asserts that `ReaderSessionGate` actually wraps the
reader routes, that `profile.tsx` calls `signOutIntent` before signing out, or that the upload screen
renders its account prompt. Delete the wiring and the mobile suite stays green.

That wiring is held by review, and by [`QA-005`](../qa/scenarios/QA-005-guest-loop.md), which covers
what no runner can reach: SecureStore write ordering, the 3 s reader gate under airplane mode, and
registering after an hour idle. It has not been run yet.

Two lanes did get better. `packages/shared` — the auth client, the progress maths and the resume
logic for *both* clients — now runs its ~380 tests and a typecheck in CI at all; `apps/web`'s Vitest
config is rooted at `apps/web`, so they were reachable only through a root `pnpm -r test` that nothing
ran, and the package had no `typecheck` script for `pnpm -r typecheck` to find. And the guest-session
permit limit moved into config (`RateLimits:GuestSessionPermitLimit`, production 3 per IP per 5 min)
so CI can raise it — the merge suites need ≥6 guests and every request there comes from one host. A
knob, not a bypass: the policy, window and partition key are the same code in both, so a regression in
the limiter still fails a test.

## Mobile — an invitation, not a red error — mobile, web — 2026-09-05

A tester installed the app from the closed-testing link and sent back a screenshot of nothing much.
That prompted an audit of what a person without an account actually meets, and the audit disagreed
with our own notes.

`docs/STATUS.md` said the first screen was a sign-in wall on Library. It is not: `(tabs)/index.tsx:35`
has sent guests to Discover since PR #453, with a comment saying so. The real shape was less dramatic
and more embarrassing — no wall at the door, and three of the four reachable tabs broken once you
walked in.

**The reader promised a button it did not render.** `ReaderTapCoachmark` fires unconditionally 600 ms
after the first reader mount, once per install, and it is the only thing in the app that teaches
anything. Its copy: *"Press and hold a word to see its translation, then tap Save to add it to your
vocabulary."* But Save lived inside the `isAuthenticated` block in `SelectionActionBar` — for a reader
with no account it was simply absent. The app's single teaching moment taught a control that was not
on screen. The `if (!isAuthenticated) return` inside `useReaderVocabActions` that was supposed to be
the guard had been unreachable for as long as the gate above it existed.

**Vocabulary called a missing account a server fault.** The screen had no auth check at all — no
`useAuth` import anywhere in the file. It fetched `/me/vocabulary/words` on mount, the request 401'd,
`isOfflineError` returned false, and the screen rendered `library.loadFailed.*`: *"Couldn't load your
library. Something went wrong on our side. Your books are safe."* — with a Retry button that 401s
again, forever. Two strings were already sitting in the locale file for exactly this case,
`vocabulary.signInPrompt` and `stats.signInPrompt`, written and never wired.

Translation and dictionary were fine throughout: neither endpoint is `/me/`-scoped. So the loop breaks
precisely at Save → Vocabulary → Review, which is the entire product, and nowhere else.

### What we ruled out

**A sign-in CTA on the guest toast.** The first cut of the fix shipped one, and adversarial review
found it was worse than the bug it replaced. Sign-in ends in `router.replace('/(tabs)/library')` —
deliberate, with its own comment block and QA history — which tears down the reader stack. Mobile
has no pending-vocabulary store, unlike web. So a guest who tapped a toast reading *"Sign in to keep
this word"* lost the word, lost their page, and landed on the Library tab. And because
`ToastContext` renders `onPress={current.onPress ?? hide}`, the whole toast is the button: swatting
it away ejected you too. The fix was to delete one property. With no `onPress`, the entire surface
becomes a dismiss and the reader stays in the book.

**Rescuing the word.** Mirroring web's pending queue would be real work thrown away in the next PR,
when a guest saves for real. The copy admits the loss instead: *"Saving words needs an account — this
one wasn't kept."* Past tense, because the tap already happened and produced nothing.

**Wiring `capabilities.ts` to anything.** It ships with zero call sites on purpose. Mobile's
`isAuthenticated` is `user !== null`, and about seventy places depend on it; a guest session flips
them all at once. Roughly sixteen of them mean *"do I have a token"* — correct for a guest, who is a
real server-side row that syncs — and only about eight mean *"is this a real account"*. A bare
`isGuest` boolean would push that judgement into every screen, which is how `profile.tsx` ended up
hiding the edit pencil behind `!isGuest` while leaving the `TouchableOpacity` under it live. The
module lands ahead of the migration so that the PR which mints guests is behaviour, not scaffolding.

### Also found, not fixed here

`GuestActivityMiddleware` is dead code. It reads `context.User.FindFirst("is_guest")`, but the API
registers no ASP.NET authentication middleware at all — auth is manual per endpoint via `GetUserId`.
`context.User` never carries the claim, so it returns early on every request and `LastActiveAt` is
only ever written at guest creation. Harmless today because mobile mints no guests. Once it does, a
guest who reads daily but saves nothing is still deleted after thirty days, because reading updates
neither `LastActiveAt` nor the cleanup worker's preservation filter, which excludes `ReadingSessions`
by design.

Two web bugs surfaced the same way, both in the code mobile is about to copy: `createGuestOnce`
swallows a failed mint with no UI signal, so a rate-limited or offline reader stays anonymous while
saves pile into IndexedDB; and `ReaderPage` calls `ensureSession()` gated on `isAuthenticated`, which
is false during auth bootstrap, so a returning user deep-linking into the reader races a guest mint
against their own session restore — burning one of three permitted mints per five minutes and leaving
an orphan row.

### What it cost, and what is still uncovered

Net −72 lines of product code. On web that was mostly deletion: a guest-limit context whose page
counter, practice counter and both limit flags had no consumers anywhere and whose flags were
therefore permanently false; a `SaveProgressPrompt` that could only ever fire for a reader whose guest
mint had *failed*; four orphaned i18n keys; and a hundred lines of CSS for a component that no longer
exists.

The honest gap: `apps/mobile` has no component or hook test lane, and its e2e suite is excluded both
from CI and from `tsc`. The decisions in this change are pure functions precisely so the one lane that
runs can cover them — and six of nine `listScreenState` cases and three of six `saveWordIntent` cases
fail against the pre-change code, so they discriminate rather than restate. But nothing executable
asserts that `SelectionActionBar` renders Save for a signed-out reader, or that the handler maps that
intent to a toast. Delete the branch and all 247 mobile tests stay green. That wiring is held by
review, and it is worth knowing which parts of this are guarded and which are merely correct.

One test was found green for the wrong reason and replaced: the vocabulary filter-row e2e assertion
passed because the filter chips rendered *above* the red error state, so it was guarding chrome
sitting on top of the dead end this change removes.

## Extension — a gate that could not fail — infra — 2026-09-02

A review of `extension/` after a month of changes elsewhere. The API surface it depends on is
intact — `/auth/me`, `/auth/device/code`, `/auth/device/token`, `/auth/refresh-mobile`,
`/me/books/clip`, `/me/books?shelf=readlater`, `DELETE /me/books/{id}` all still exist, the
`ClipRequest` DTO still matches field for field, the `clip` rate-limit policy is registered, and
the oversize-article error reaches the popup as its own words rather than a bare status code. The
`/connect-extension` override of the backend's `/device` is deliberate; both routes exist and both
render `DeviceVerifyPage`.

What was not intact was the checking.

`extension/README.md` documented a gate — a `for` loop running `node --check "$f"` over every
script, to be run "before loading or committing". Two things were wrong with it.

**Nothing ran it.** No workflow in `.github/` mentions the folder. The extension has no build step
and no `package.json`, so nothing else was going to look at it either.

**It could not have failed.** Appending `const x = ;` to `background.js` and running the documented
command exits **0** on Node 24 — module-syntax detection swallows the parse error when the file is
passed by path. Piping the same bytes through stdin with `--input-type=module` reports it. So even
a developer who remembered the instruction would have been told the extension was fine.

`scripts/check-extension.mjs` now runs in CI and checks three things:

1. **Every `.js` parses**, through stdin, the way that actually reports errors. Without a build
   step, a typo in `background.js` ships a service worker that never starts.
2. **The manifest names only files that exist.** A renamed icon or page makes Chrome refuse to load
   the entire extension, and no syntax check can see that.
3. **`host_permissions` carries no localhost.** The README tells developers to add
   `http://localhost:8080/*` for local work and to remove it before packaging — a rule previously
   enforced by memory.

Each of the three was verified by breaking the extension on purpose and confirming the check said
so. The first one is why: it passed the deliberate syntax error on the first attempt, which is how
the underlying `node --check` behaviour was found at all.
<a id="2026-09-03-mobile-crash-reporting-stops-being-dormant"></a>

## Mobile — crash reporting stops being dormant — mobile — 2026-09-03

`apps/mobile/src/lib/sentry.ts` has been complete for weeks — scrubbing, `dist` set to the update id
so a JS-only fix is distinguishable from the native build it landed on, `sendDefaultPii: false` to
keep the Data Safety answers honest. It did nothing, because `EXPO_PUBLIC_SENTRY_DSN` was never set
and the file's own contract is that an absent DSN is a complete no-op.

So while build 24 sat on two testing tracks, **nothing anywhere was recording a crash.**

Project `textstack-mobile` created in the `textstack` org, beside the existing `dotnet-aspnetcore`.

### Where the DSN lives, and why it is not in the repository

The obvious home is an `env` block in `eas.json`. That would have been wrong in a way that only
shows up later: `eas.json` `env` applies to **builds**, and this project ships through **updates**.
The DSN would have been present in the next Play build and absent from every OTA — which is how
almost everything reaches users here. Sentry would have looked configured and stayed silent.

It is an EAS environment variable instead, on `production` and `preview`, which both `eas build` and
`eas update --environment production` read. The CI OTA job already passes that flag.

A DSN is a public client key — it is compiled into the app bundle by design and identifies a project,
not a person. It is not in the repository because of where it needs to be read from, not because it
is a secret.

### A measurement that lied, and why

Checking whether this moves the runtime fingerprint gave `7c9304f7…` against the expected
`1065515f…`. Not the env var: `npx expo run:android` had generated `apps/mobile/android` and `ios`
earlier in the session, and those directories — gitignored, absent from any clean checkout — are
fingerprint inputs. The same hash had already appeared in the emulator's dev-client menu, which is
what gave it away.

An EAS environment variable lives on EAS servers and is not in the repository at all, so it cannot
move a fingerprint computed from the repository. The authority is the `mobile-runtime` CI job on a
clean checkout, and the OTA workflow's own guard, which refuses to publish into a runtime nobody has
installed.

## Security — alerts on, and a lockfile that was hiding things — infra — 2026-09-03

`docs/STATUS.md` had carried "Dependabot alerts are still disabled" for three revisions. Checked
rather than remembered:

```
GET /repos/mrviduus/textstack/vulnerability-alerts  → 404   (off)
GET .../dependabot/alerts                           → 403   "alerts are disabled"
```

A separate switch from `.github/dependabot.yml`, which handles scheduled *version* updates and works
fine. Alerts are what says a dependency has an advisory, and their absence is how a patched
`dompurify` — the XSS sanitiser itself — sat available for months while the vulnerable version
shipped to every visitor. The declared range already allowed the fix; only a stale lockfile held it
back.

They are on now. Automatic security *pull requests* stay off: the same day recorded "a bot that
merges its own dependency updates" as deliberately not done, and visibility was the missing half.

### Turning them on found something

Fourteen alerts, where `pnpm audit` reported three. Eleven of them named one manifest:

```
packages/shared/pnpm-lock.yaml   — last written 2026-05-24
```

Orphaned by the move to a pnpm workspace three months later. `packages/shared` is a workspace member
and declares `vitest: catalog:`; it resolves through the root lockfile and installs nothing from its
own. But the file was still committed, still pinning `vitest 2.1.9`, `vite 5.4.21`, `postcss 8.5.10`,
`nanoid 3.3.11` and `esbuild 0.21.5` — including a **critical** advisory — where any scanner reading
the repository would find them.

Neither tool was wrong. `pnpm audit` read the tree that gets installed; GitHub read a file that gets
committed. They disagreed because they were reading different files, and the disagreement is what
surfaced the dead one. Deleted; `pnpm install --frozen-lockfile` is unaffected.

### The gate

`scripts/check-advisories.mjs` runs in CI beside `check-node-version.mjs` and `check-extension.mjs`.
A setting somebody can switch off is not a check, and the three permanent advisories would otherwise
train everyone to stop reading the alert list. Three ways to fail, each verified by breaking it:

1. **An advisory nobody wrote down** — fails with package, GHSA id, and where to record it.
2. **A listed advisory that stopped being reported** — fails asking for the entry's deletion, because
   an excuse that no longer applies is worse than no excuse.
3. **A second lockfile** — fails, naming the file. This is the finding above turned into a rule.

The lockfile check asks git, not the filesystem: a lockfile someone has lying around untracked is
their business, a committed one is the repository's. Walking the tree was tried first and died on a
broken CocoaPods header symlink under `apps/mobile/ios/Pods`, which is its own argument for the
narrower question.

The .NET half is one step in the existing `backend` job — `dotnet list package --vulnerable
--include-transitive`, currently clean across all 15 projects. It reports without failing, so the
grep on `> ` is what makes it a gate; that pattern was checked against a real vulnerable listing and
against clean output before shipping.

## Reader — tapping an image opens it again — mobile — 2026-09-02

Every script `readerHtml.ts` emits sits inside `<head>`. The image-lightbox setup is an IIFE that
runs as the parser reaches it — before `<body>` exists — and its **last statement** was:

```js
document.body.addEventListener('click', function (e) { … })
```

`document.body` is null at that moment, so it threw
`Cannot read properties of null (reading 'addEventListener')` on **every reader load**, in every
book. Because it was the last statement, nothing downstream broke visibly. The reader looked
perfect. Tapping an image simply did nothing, and had never done anything.

Delegated on `document` instead. Click bubbles there, so the behaviour is identical, and `document`
exists while `<head>` is being parsed.

The error had been sitting in
[`2026-09-01-android-tts-selection.md`](../qa/reports/2026-09-01-android-tts-selection.md) under
"found while here, not fixed", with the note that "something is being wired up that silently is
not". This is what.

### The test, and the test that was too clever

The rule you want is "nothing touches `document.body` before `<body>` exists". That is not a rule a
string search can enforce: most body access in the head script is inside functions that run later,
and a first attempt duly flagged `document.body.appendChild(sep)`, which is fine. Telling them apart
needs a parser.

So the test pins the construct that actually broke, and its comment says why it is narrow. It was
verified the only way worth trusting: by putting `document.body` back and watching it fail.

<a id="2026-09-02-updates-a-fix-lands-without-two-restarts"></a>

## Updates — a fix lands without two restarts — mobile — 2026-09-02

An over-the-air update used to need **two** cold starts. `fallbackToCacheTimeout: 0` means the app
never waits at the splash screen, so the first launch downloads the bundle and the second one runs
it. Nobody restarts an app twice to collect a fix, so in practice the update arrived days later, or
whenever the phone rebooted.

The obvious lever is `fallbackToCacheTimeout`, and it is the wrong one twice over: it blocks every
launch on the network to serve the rare launch with an update waiting, and it lives in `app.json` —
a fingerprint input, so shipping it would need a store build. This is JS, so it travels as an update
itself.

`AutoUpdater` checks at startup and whenever the app returns to the foreground, downloads, and
reloads.

### Except while someone is reading

This app's premise is uninterrupted long-form reading, and a restart mid-chapter is the one
interruption it cannot justify to itself. So the update waits on `/reader` and `/my-books/read`.

That deferral is only half a rule. An update that arrives during a long reading session has to land
when the reader is closed, or "wait" quietly becomes "never" for exactly the people who use the app
most. A second effect watches the route and applies as soon as it changes to something that is not
reading.

The policy is a pure function in `apps/mobile/src/lib/updateApply.ts` with four tests, including the
prefix-matching one — `/readers-club` is not the reader, and `/my-books/9` is a detail screen while
`/my-books/read/9` is not.

### What is not verified

`__DEV__` disables the whole component, so a development build cannot exercise the path that
matters. What the emulator confirmed is that it does nothing in development: the app launches

## Profile — the build number survives an update — mobile — 2026-09-02

Two corrections to the version footer shipped hours earlier, both from putting it on a screen.

### It was where nobody looked

The footer sat below Sign Out and the danger zone — past six rows, off the first screenful. The
first person to look for it did not find it.

The build number now rides the **About** row as a trailing value:

```
ⓘ  About                    1.0.0 (24)  ›
```

That is a pattern the screen already uses — `I know · Русский` sits the same way — so it reads as
part of the list rather than an addition to it. The update line stays at the foot, because it
answers a different question and only matters when it disagrees with the build.

### The number used to vanish exactly when it was needed

The first version read `versionCode` from `Constants.expoConfig`, which carries what EAS wrote at
build time. An update published by `eas update` has no such field — so the number would disappear
after the first OTA, which is precisely the moment someone is trying to say which build they hold.

`expo-application` reads it from the installed package instead. It is a native module, and the
earlier write-up rejected it for that reason: a native addition moves the runtime fingerprint, and
a change whose whole purpose is telling testers what they have would then need a store build to
reach them.

That reasoning was sound and the premise was wrong. `expo-notifications` already depends on
`expo-application`, so it is compiled into the APK already. Measured rather than assumed:

```
baseline:              1065515fb7b75ee76efe35c56ec1d6ced76a8bc3
with expo-application: 1065515fb7b75ee76efe35c56ec1d6ced76a8bc3
```

Identical. The fingerprint hashes the resolved native module set, not the direct dependency list, so
this still travels as an OTA — and the number now names the installed APK on both sides of one.

### And it called a development build an update

Shown on the emulator as:

```
TextStack 1.0.0 (1)
Updated over the air
```

`(1)` is the debug APK's versionCode, which is the new reading working. The second line was wrong:
a development build has expo-updates configured, so `isEnabled` is true, while `isEmbeddedLaunch` is
false because the bundle came from Metro. The previous guard tested only the first. Now gated on
`__DEV__` as well, and it reads `Development build`.

Three defects in this footer so far, and all three were found by opening the screen — none by the
types, the tests, or reading the diff.

## Profile — which build is this — mobile — 2026-09-02

Two quiet lines at the bottom of Profile:

```
TextStack 1.0.0 (24)
Bundled with the app
```

The app could not answer "which build am I holding" from inside itself. Play Console shows a
versionCode; the app showed nothing. That gap cost real time the day a tester was asked to confirm
a fix and the only way to check was to open the store listing.

The second line exists because there are **two** things that can be out of date, and they fail
differently. The native build is replaced only through Play. The JS bundle arrives on its own over
the air — and when the runtime fingerprint moves, it stops arriving with no visible sign. A tester
reporting "still broken" needs to say which of those they are on, and now can.

### What the render check found that the types did not

Written, typechecked clean, tests green — and then two defects, both found only by looking at the
screen:

- **The signed-out branch is a separate early return**, and the footer was not in it. The person who
  cannot sign in is precisely the one who needs to report their build number.
- **It called a dev client an over-the-air update.** `Updates.isEmbeddedLaunch` is `false` when
  expo-updates is not running at all, which reads as "an update is applied" in the one context where
  none can be. Gated on `Updates.isEnabled` — and then on `Platform.OS` too, because the web shim
  hardcodes `isEnabled = true` and `isEmbeddedLaunch = false`, so on web the pair asserts an update
  that cannot exist. Web is the dev preview and the e2e harness here, never a shipped target.

### Two decisions worth stating

**No `expo-application`.** It reads the versionCode from the installed APK, which is strictly more
correct than the manifest. It is also a native module, so adding it would move the runtime
fingerprint — and a change whose entire purpose is telling testers what they have would have needed
a store build to reach them. The manifest value is honest instead of merely available: EAS writes
`versionCode` at build time, so it is present in the bundle shipped inside the APK and absent from
one published by `eas update`. Running embedded, the number is the build you installed. Running an
OTA, there is no build number to state and the second line says so.

**The date is formatted by hand.** Hermes ships without full ICU unless the build opts in, and
`toLocaleDateString('en-GB', …)` drifts with the ICU version — `2 Sep 2026` on one machine,
`2 Sept 2026` on another. This string gets read back over chat; it should be the same everywhere.

Logic in `apps/mobile/src/lib/buildInfo.ts` with six tests, following the same shape as
`ttsRequest.ts`: the decision is a pure function, the screen only renders it.

## CI — dependencies refresh themselves weekly — infra — 2026-09-01

Four sibling repositories already run a weekly job that bumps NuGet packages and pushes straight to
`main`, verified inside the job. Copying it here would have been wrong for one reason: in those
repos a push to `main` publishes a package, and in this one **it deploys production**. So these
lanes open pull requests, and CI — 1328 unit tests, e2e, both images built — is the gate.

**The lane that matters changes no version at all.** `dompurify` shipped a known-vulnerable XSS
sanitiser to every visitor for months while `apps/web/package.json` already declared a range that
allowed the fix. The range was right; nothing re-resolved it. So `refresh` re-resolves the lockfile
inside the ranges already declared and touches no manifest. No amount of version bumping would have
found that.

`catalog` raises the shared catalog by patch and minor. One entry moves every workspace member,
which is what makes it worth automating. Majors are reported and left for a person — of the seven
updates available on the day this was written, all seven were majors, so the job's first real
output is a list of things it refused to do.

`react`, `react-dom` and `@types/react` are excluded outright. They decide the mobile runtime
fingerprint: a bot bump passes CI, because `tsc` and the unit tests do not know what an SDK
compatibility matrix is, and then every installed app stops receiving OTA updates because
`mobile-ota.yml` correctly refuses to publish into a runtime nobody is running. `refresh` cannot
reach them either, since it never changes a declared range.

Both lanes verify with a **Metro bundle** before opening anything. `tsc` and the unit tests pass
while an app cannot be bundled at all — module resolution only breaks when Metro walks the graph,
and moving dependencies is precisely what moves module resolution.

The decision lives in `scripts/catalogBump.mjs` as a pure function with tests, because a judgement
that runs unattended every Monday is one worth being able to exercise. The tests earned it
immediately: the first version compared the *installed* version reported by `pnpm outdated` while
rewriting the *declared* one, which are different numbers and not always the same distance from
`latest`. They also cover the case that would be worst — a patch bump of `react` sailing through —
and the one that is easy to get wrong, a `name: value` line under `packages:` or `allowBuilds:`
looking exactly like a catalog entry to anything reading line by line.

Wiring those tests into CI needed its own step: no vitest project reaches outside its own app, so
`scripts/catalogBump.test.mjs` would have existed and never run.

<a id="2026-09-02-ssg-something-watches"></a>

## SSG — something finally watches whether pages are being regenerated — infra — 2026-09-02

`docs/STATUS.md` has carried this line since 2026-08-11: *"No SSG freshness alarm. The five-week
outage was found by a screenshot. Nothing yet alerts on 'newest generated page is older than N
hours' — the single change that would have caught it on day one."*

Three incidents later it is the single change that would have caught all three. It exists now.

`/health/ready` already reported per-component status for ops, so `ssg` joins `db`, `storage` and
`ollama` there: when the last rebuild succeeded, how many hours ago, and whether the most recent run
failed. Reported, never fatal — stale pages are an SEO problem, not a reason to fail a probe that
gates traffic. The judgement lives in `health-check.yml`, which runs every five minutes and already
had somewhere to put it.

**Two failure modes, two patiences.** A *failing* rebuild is a malfunction whatever the cadence —
the next one will not help either — so it alarms at once. *Staleness alone* needs a generous window,
because rebuilds here are deploy-driven rather than scheduled. The threshold is not a guess:
production history shows a healthy 19-hour gap between rebuilds on a quiet day, so 72 hours sits
well past anything normal and still catches nothing-for-five-weeks.

Exercised against all five real shapes before shipping — healthy, the measured 19-hour quiet day,
yesterday's failing run, a five-week outage, and a fresh install with no rebuilds on record. The
quiet day is the one that matters most: an alarm that cries on a normal Sunday gets muted, and then
it is not an alarm.

A missing `ssg` field is treated as "the API predates this check" and warns rather than fails, which
is the normal state for the forty minutes between merging it and the deploy finishing.
<a id="2026-09-02-ssg-worker-honest-health"></a>

## SSG — a worker that fails every job stops calling itself healthy — infra — 2026-09-02

`docker compose ps` said `ssg-worker Up 7 hours (healthy)` while every rebuild it attempted died on
`EACCES` and the site served pages nobody had regenerated. That is not a lie the container told; it
is the question the healthcheck asked. It looked for a heartbeat file the poll loop touches every
30 seconds — liveness, and nothing else. A process that is running and getting nothing done answered
yes.

The loop now records the outcome of each job beside the heartbeat, and the healthcheck wants both:
recent heartbeat **and** a last job that did not fail. Written inside `setJobStatus`, the one funnel
every outcome passes through including the `catch`, so a future code path cannot forget to.

An absent marker means nothing has run yet. That is the normal state of a fresh container and must
not read as failure — it is the case worth getting right, because getting it wrong makes every
deploy look broken for the first few minutes and teaches everyone to ignore the signal.

All four states exercised before shipping: fresh container, last job completed, last job failed,
and heartbeat gone stale.

Nothing depends on this container being healthy, so the change is informational rather than
operational — which is the point. `docker compose ps` was the first place I looked during the
incident, and it was reassuring.

## Infra — one workspace, one catalog — infra — 2026-09-01

The backend has had central package management the whole time: `Directory.Packages.props`, one
version per dependency, no `<Version>` in a csproj. It is also the half of this repo with **zero
vulnerable packages and no version drift**. The JS side had no equivalent because it had nowhere to
put one — no root `package.json`, no `pnpm-workspace.yaml`, `apps/web` and `apps/admin` each with
their own lockfile, `apps/mobile` on npm entirely. Three projects sharing a directory.

Six dependencies were declared at different versions in different places: `typescript` 5.6.3 against
5.9.2, `@playwright/test` 1.52 against 1.60, `react` 19.2.0 against 19.2.6.

Now one workspace and one lockfile, with `pnpm-workspace.yaml` carrying a `catalog:` — the direct
equivalent, referenced as `"typescript": "catalog:"`. Thirteen shared packages converge:
TypeScript 5.9.3 everywhere, Playwright 1.62.1 everywhere. `packageManager` in the root
`package.json` does the same for pnpm itself, which had drifted across `pnpm@9`, `pnpm@9.15.0` and
`version: 9` — the admin Dockerfile already carried a comment about hitting corepack drift.

### Three things that only surfaced by running them

**pnpm 11 reads its settings from `pnpm-workspace.yaml`, not `.npmrc`.** `node-linker=hoisted` was
set in `.npmrc` and silently ignored — `node_modules/.modules.yaml` still said `"isolated"`. The
same relocation had already turned `pnpm.onlyBuiltDependencies` in package.json into `allowBuilds`,
which is why `pnpm -C apps/web build` had been failing locally with `ERR_PNPM_IGNORED_BUILDS`. Both
now live where pnpm looks.

**Metro needed the middle ground.** `watchFolders` listed `packages/shared` alone, which worked
while there was no workspace; once one existed, Expo resolved against the workspace root and the
entry point failed with *"Unable to resolve module ./apps/mobile/node_modules/expo-router/entry"* —
present on disk, invisible to Metro. Watching the workspace root fixed that and broke the file map
instead (*"../web/node_modules/esbuild already exists in the file map as a file"*), because Metro
then walked another app's dependencies. It watches `packages/` and the root `node_modules`, and
nothing belonging to the other two. `resolver.disableHierarchicalLookup` — the usual monorepo advice
— is deliberately not set: pnpm packages find their dependencies by walking up out of
`node_modules/.pnpm/<pkg>@<version>/`, and cutting that off resolves the entry and fails one import
later.

**Leaving Expo in charge of React did not survive.** `react` and `react-dom` were carved out of the
catalog at first, since `expo install` pins them against the SDK matrix. Hoisting can only put one
copy at the root, so with mobile on 19.2.0 and web on 19.2.8 the root ended up holding react 19.2.0
beside react-dom 19.2.8 — a mismatched pair, and 26 web tests failed with *"Invalid hook call …
more than one copy of React"*. One React now: React Native 0.83.2 declares `react: ^19.2.0`, which
19.2.8 satisfies, and the exact number is what `expo install` writes rather than a floor the runtime
enforces.

### Production images build from the root

A workspace has one lockfile, and `catalog:` cannot be resolved without `pnpm-workspace.yaml` in
scope — so an image built from `apps/admin` or `apps/web` alone can no longer install anything. Both
build contexts moved to the repository root and copy every member's manifest, because
`--frozen-lockfile` validates the lockfile against all of them. The repo layout is kept inside the
image (`/repo/apps/...`) rather than flattened, so the compose volume and `ssg-worker.mjs` paths stay
recognisable.

`apps/web/Dockerfile` and `apps/web/Dockerfile.ssg` were deleted. Nothing referenced them — not
compose, not the Makefile, not CI — and after this change they could not have worked either. One of
them was still described in `docs/02-system/ssg-prerender.md` as the image carrying Chromium, and
reading it is part of how the "EOL Node in production" alarm got its scope wrong.

Verified end to end: 759 web tests, 366 shared, 203 mobile, `tsc` clean, both site builds, and a
full Metro bundle — the check that actually exercises module resolution, and the one that caught
every problem above.

<a id="2026-09-01-ci-an-ota-goes-out-on-merge"></a>

## CI — an OTA goes out on merge, and refuses to when it would reach nobody — infra — 2026-09-01

Shipping a JS-only mobile change meant running `eas update` from a laptop. `mobile-release.yml`
already had an `ota-update` action; it went unused because the `EXPO_TOKEN` secret has never been
set, which is still the one thing blocking every EAS path in CI.

New workflow `mobile-ota.yml` publishes to the production channel on any push to `main` touching
`apps/mobile/**` or `packages/**`. Kept separate from `mobile-release.yml` rather than bolted onto
it: that file's header states it is `workflow_dispatch` only so nothing reaches the store without a
human clicking, and that remains true — an OTA republishes the JS bundle to apps already installed
and never touches the store.

The guard is the reason the file exists. `app.json` sets `runtimeVersion.policy: "fingerprint"`, so
an update only lands on builds whose runtime matches. When a merge moves a native dependency, a
config plugin or `app.json`, the runtime moves with it — and `eas update` **still succeeds**,
publishing into a runtime nobody has installed. A green check and zero delivery, with nothing else
in the system positioned to notice. It is the shape of the
[SSG rebuild that reported success after losing its files](../incidents/2026-08-31-deploy-wiped-a-running-ssg-rebuild.md),
and worse, because that one was eventually visible on the site.

So the workflow resolves the runtime, compares it with the newest finished Android production build,
and publishes only on a match. A mismatch **fails the run** with what to do instead. Failing is the
deliberate choice: a skipped step and a delivered update look identical in a green tick.

Two things are decided rather than guessed, since neither can be tested before the token exists: the
production build is selected in `jq` on `buildProfile`/`channel` rather than through a CLI filter
flag that has been spelled both `--profile` and `--buildProfile` across EAS versions, and the missing
token is detected by reading it from `env` rather than a step-level `if`, where the `secrets` context
is not dependably available. The commit message reaches `eas update` through `env` too — it is
attacker-controlled text, and `${{ }}` inside a `run:` block executes what it contains.

`docs/03-ops/play-store-release.md` promised `npm run check:runtime-version` "if it has been wired
up". It never was; the runbook now points at the workflow that does it.

Untested end to end, and cannot be until `EXPO_TOKEN` is set — which is why `workflow_dispatch`
carries a `dry_run` input, defaulting to on, so the first run compares without publishing.

**Update, same day.** The token landed and the first run failed before reaching any of the above:
`eas-cli@23.2.0` pulls `@oclif/plugin-autocomplete`, which declares `engines.node >= 22`, and yarn
refuses to install it on the Node 20 both workflows pinned. `mobile-release.yml` carried the same
pin, so the manual OTA path had a second reason not to work beyond the missing secret — and neither
workflow had ever run far enough to find out. Both now use Node 22.

<a id="2026-09-01-selection-extending-a-long-press-reaches-the-app"></a>

## Selection — extending a long-press into a sentence reaches the app — mobile — 2026-09-01

Found on an emulator while verifying the speech fix, and it turned out to be the defect that
actually decided what got read aloud. The reader could select a sentence and have Listen read a
single word — not because speech picked the wrong text, but because the app never heard about the
sentence.

After the 450 ms hold selects a word, dragging the handles out to a phrase fires `selectionchange`.
Every one of those events landed inside the 1500 ms suppression window the tap path arms, so all of
them were dropped and the app's selection stayed on the word. Listen, Translate and Explain all
acted on that word, and Ask stayed hidden because `isMultiWord` was still false.

Confirmed by nudging a selection handle *after* the window had expired: the identical event
delivered the full sentence immediately.

| | |
|---|---|
| word selected (long-press) | `12:18:18.349` |
| suppression window closes | `≈12:18:19.849` |
| debounced dispatch would fire | `≈12:18:19.82` |

Thirty milliseconds inside. That margin is why the report was "it behaves differently on different
phones" — a device that completes the drag slightly slower lands on the other side of the window and
works fine.

The release path built to prevent exactly this — `touchmove` zeroing the deadline once the finger
passes `SELECT_EXTEND_TOLERANCE` — carries the comment *"Needs on-device validation of the
extend-from-tap gesture"*. It was never validated, and it does not fire: once Android's selection
ActionMode owns the gesture, the page stops receiving `touchmove` at all.

The window now gates only what it was built for. A collapse inside it is the ActionMode going away;
an echo of a selection we made ourselves repeats text the existing dedupe already drops. Neither can
produce a *different, non-empty* selection, so that one is dispatched regardless.

Reproducing it needs `adb shell input motionevent`, not `input swipe`: swipe starts moving
immediately, the finger passes `DRAG_TOLERANCE` at 8 px, and the word timer is cancelled before it

<a id="2026-09-01-reader-speech-starts-when-asked"></a>

## Reader — speech starts when asked, and the button reads what you picked — mobile — 2026-09-01

A tester on a Galaxy S24 reported that selecting a sentence and pressing Listen produced silence, or
a cut-off word, depending on timing. Tapping a single word worked. The phrasing that reached us was
"the voice breaks off", which pointed at the audio, and the audio turned out to be fine.

Production `/api/tts` was measured first, because a truncated MP3 would have explained everything:

| input | response | bytes | duration |
|---|---|---|---|
| 44 chars | 200 | 22 KB | 3.72 s |
| 375 chars | 200 | 123 KB | 20.52 s |

Whole file, 1.18 s to synthesise. Nothing server-side was cutting anything off. Three client
defects were stacking into one symptom.

**The word spoke itself.** A single-word selection auto-played. The message carrying it is posted by
the 450 ms long-press in `readerBridge.ts` — which is also the first frame of the drag that selects a
sentence. So the gesture that means "I am choosing a phrase" began by reading its first word aloud,
under a finger that had not finished moving. On a device with Samsung's own long-press timing this
lands differently than on a Pixel, which is why it looked device-specific.

**Then the button meant the wrong thing.** `toggle` branched on a single boolean — something is
playing, so stop. That is correct for the button that started the sound and wrong for every other
one. With the word still playing, pressing Listen on the sentence was read as "stop the word", and
the sentence never played at all. A second press worked, because by then nothing was playing. That
is the whole of "it works every other time".

**And the wait was invisible.** Fetching audio takes about a second on a first play. The button said
Listen throughout, so the natural response — press it again — cancelled the fetch that was already
running. Even with the comparison fixed, that press would still have read as stop.

The decision now lives in `apps/mobile/src/lib/ttsRequest.ts` as a pure function over
`(phase, currentText, requestedText)`, tested, following `pdfWritePolicy.ts`. It is a small piece of
logic to extract, and it is extracted because the path around it can only be exercised on a phone:
`apps/mobile/e2e` runs Chromium against `expo start --web`, where there is no `expo-audio` and no
native long-press, so nothing automated reaches the reader's speech path.

Auto-speak is gone rather than rescued. It was the root of the race, and unrequested audio during a
selection gesture is the thing the reader is supposed not to do. Speech now only ever starts from a
button. The web reader was already right on all three counts — `speak()` there begins with `stop()`,
and `isLoading` has always been separate from `isPlaying` — so this is mobile catching up to a
contract that already existed, not a new design.

Deleting the sentence button was considered and rejected: it would not have fixed anything. The word
would still have spoken itself mid-drag; there would simply have been no way left to hear the
sentence.

None of this was the whole story, which is the argument for testing a fix rather than reasoning it
closed. Verifying on an emulator showed the sentence was not reaching the app at all — see the entry
above. Speech had been reading the only text the app had.

## Selection — a long passage stops disappearing instead of opening a toolbar — mobile — 2026-09-01

Found while tracing the speech bug. Selecting more than 300 characters posted no message to the app

<a id="2026-08-31-search-a-common-word-stops-timing-out"></a>

## Search — a common word stops timing out, because ranking happens after deduplication — backend — 2026-08-31

Sentry reported two `NpgsqlException: Timeout during reading attempt` from `PostgresSearchProvider`
within the same second. Reproduced immediately: `?q=war` returned **500**, `?q=love` took 4.9s,
`?q=dracula` took 158ms. The provider's command timeout is 5s, so anything above it is a 500 to the
reader.

The index was not the problem, which is worth stating because it is where one looks first. The GIN
index on `chapters.search_vector` is valid, 91 MB, and matches 23,487 of 40,589 chapters for *love*
in 9ms. Measured against the same rows:

| | |
|---|---|
| match only | 9 ms |
| match + `ts_rank` + order | **7,747 ms** |
| `ts_headline` on the 20 output rows | 48 ms |

`ts_rank` reads the tsvector of every row it scores and no index can help it, so strategy 4 was
paying for 23,487 scores to return ten results. `ts_headline`, the usual suspect, is cheap here.

The obvious cheap fix is to cap the candidate rows, and it is a trap: 500 chapters in heap order are
consecutive chapters of the same few books, so ranking a 500-row cap finds 36 of the 1,334 books that
actually match. Deduplicating first costs a sort on `edition_id` and leaves exactly one row per book
— 1,334 scores instead of 23,487, same 1,334 books, 70 ms.

End to end against production, the whole CTE with all four strategies and headlines: **125 ms**, with
*Sons and Lovers*, *Women in Love* and *Love's Labour's Lost* at the top where they belong.

The trade is which chapter represents a book: the first match by `DISTINCT ON` rather than the
highest-scoring one, so an edition's score comes from one of its matching chapters rather than its
best. Recovering that would mean ranking all 23,487 again, which is the cost being removed.

Pre-existing, not new — it only ever surfaced on words common enough to match half the corpus, and
search sends this site one visitor a month. It became visible because an SSG rebuild put the box
under load and pushed a 4.9s query past 5s.

<a id="2026-08-31-android-the-launcher-icon-stops-being-a-solid-block"></a>

## Android — the launcher icon stops being a solid block for anyone using themed icons — mobile — 2026-08-31

The first closed-testing tester installed the app and reported two things. One of them was "и ярлык
чёрный".

An adaptive icon is layers, and Android composites them by alpha. Both of ours had none.
`android-icon-monochrome.png` was a 432×432 image that is 100% white with alpha 255 on every pixel —
blank, and fully opaque. Themed icons take that layer, read its alpha as the shape and fill it with
the wallpaper's accent: an alpha of 255 everywhere means the shape is the entire tile, so the
launcher drew a solid rectangle, dark on a dark theme. Nobody had seen it because themed icons are
opt-in and off by default; the tester had them on.

The same defect, less visibly, in `android-icon-foreground.png`: greyscale, no alpha, 91% white
around a dark T. Being opaque it covered the background layer completely, which is why
`adaptiveIcon.backgroundColor` (`#F3EEE7`) and `android-icon-background.png` had never once been
visible. The icon was a white tile that happened to look deliberate.

Both layers are now the T as a real silhouette: alpha 0 outside it, 255 inside, 8.8% coverage — the
foreground keeping the mark's own `#2B2B2B` so the configured background finally shows through, the
monochrome white because the system tints by alpha and ignores colour. Geometry is untouched; this
is the same T in the same place, cut out rather than painted on.

Icons are a native resource, so this needs a build — an OTA cannot carry it.

<a id="2026-08-31-beta-the-android-invite-works-on-the-live-site"></a>

## Beta — the Android invite works on the live site, where chapter URLs end in a slash — web — 2026-08-31

The banner shipped an hour earlier was inert in production, and the way it failed is the useful part.

Its one interesting rule — wait until the visitor has opened a book, never interrupt them while they are in one — is decided by a single pattern matched against the pathname, anchored on the chapter segment: `/books/[^/]+/[^/]+$`. Under `vite preview`, where it was verified, `/en/books/twelfth-night/2-act-i` is exactly what the router sees and the pattern matches. On textstack.app nginx 301s that URL to `/en/books/twelfth-night/2-act-i/`, and an anchored `[^/]+$` cannot match a path ending in a slash. So the read flag was never recorded, the banner never appeared for anyone, and — the half that would have been worse had the first half worked — it would not have hidden itself inside the reader either.

Both failures are the same missing character. The pattern now allows an optional trailing slash, and the negative case that keeps it honest is `/en/books/twelfth-night/` — the book page, also slash-terminated, which must still show the banner because it is not the reader.

A test now pins all of it: platform, the two preconditions, dismissal, and the reader paths in both slash forms. The bug was reachable only through a production URL shape that the local preview does not produce, which is the argument for the test rather than another manual pass.

<a id="2026-08-31-beta-the-site-invites-android-readers"></a>

## Beta — the site invites Android readers into the closed test, but only ones who have opened a book — web — 2026-08-31

The obvious places to ask are the tester-swap groups on Telegram; the honest arithmetic says otherwise. <a id="2026-08-29-resume-the-locator-decides-on-every-screen"></a>

## Resume — the locator decides on every screen that offers to continue, not just one — mobile — 2026-08-29

`#496` established the rule and applied it in one place. A progress row's `chapterSlug` is not something any client sends: the API derives it by joining the row's `chapterId` to the chapters table, and `chapterId` stops moving the moment infinite scroll carries the reader past the chapter whose URL they opened. The locator, written from the chapter actually on screen, is the half that tracks reality. The book screen was taught to prefer it. The library shelf and the "Continue Reading" rail were not, and both were still reading `server.chapterSlug` straight off the DTO.

That is how QA's 45% became 0.66%. A row can hold `locator: scroll:4-act-iii:7488` with a `chapterId` still pointing at act one; the shelf opens act one; `loadPosition` requires the locator's slug to match the chapter being opened, finds it does not, and returns nothing; the reader lands at the top with "nothing to restore", which legitimately opens the write gate; and the first automatic save writes `scroll:2-act-i:0` over a half-read play. Every step is correct in isolation. The wrong turn was made on the first one.

The obstacle to fixing it was that neither screen has a chapter list — both work from a progress row alone — and `resumeChapterSlug` validated both candidates against a list before ranking them, so with no list it answered "no idea" and the callers fell back to the field it exists to distrust. The rule now separates ranking from validation: with a list, a candidate must name a chapter that exists; with no list, there is nothing to check against and the ranking is all there is, so the locator still wins and the stored slug is still the fallback. A slug that may be stale beats sending the reader back to chapter one. This also means passing a list that has not loaded yet behaves like passing none — the answer comes sooner and corrects itself when the list arrives, which on the uploaded-book screen replaces half a second of "Start Reading" on a book the reader is halfway through.

Also from the same report, and the same theme: the book screen now shows how far in the reader is. The shelf card said "11% complete" while this screen offered a bare "Continue Reading" — same reader, same book, one of the two screens keeping it to itself. It reuses `storedBookPercent` and `formatBookPercent` exactly as the uploaded-book screen already does.
<a id="2026-08-29-progress-a-row-stops-being-able-to-contradict-itself"></a>

## Progress — a row stops being able to contradict itself — mobile — 2026-08-29

The write side of the same rule, closing the way the contradiction could be created again. A progress row carries a locator and a chapter id, the server derives the chapter slug from the id, and the two must name the same chapter or every consumer of that slug is wrong in a way nothing on the row reveals.

`#496` made the id follow the chapter on screen by looking the visible slug up in the book's chapter list, and fell back to the route chapter's id when the list could not answer — reasoning that a position saved against a slightly stale chapter beats a position not saved. On a cold open that fallback is not stale at all: the reader has not moved, the visible slug *is* the route slug, and the route id is exactly right. The case it misses is the other one. Infinite scroll fetches `chapter.next` by itself and needs no chapter list, so a reader whose book request failed — offline, a transient error, a slow link — can spend an entire session moving through chapters while `chapters` stays empty, and every save pairs the route id with a locator naming a chapter further on.

So the fallback now asks the question that distinguishes them: is the reader still where the route put them? If yes, the route id is used as before. If not, the server write is held back rather than sent contradictory, and the local record — which is keyed and resumed by slug, and is the position either way — is written as usual. The deferred write goes out when the chapter list arrives, via a one-shot effect on the transition from no list to a list. That is a different signal from the deferred-save replay already in `useReaderPersistence`, which waits on the route chapter's own id and has long since fired by the time this matters.
<a id="2026-08-29-reader-a-restore-now-says-when-it-has-landed"></a>

## Reader — a restore now says when it has landed, and nothing is saved before it does — mobile — 2026-08-29

QA opened a book at 45%, pressed back inside a second, and the stored position was 0.66%. Twice, on both entry points, with the loss scaling to how far in the reader had got — 45.2% and 40.3% both collapsed to 0.66%, while 11% dropped 1.5 points at a time and kept dropping on each repeat. A normal fifteen-second visit drifted 21px, so the damage was specific to leaving early.

**The gate added the day before was guarding the wrong instant.** `#497` made the mobile reflow reader refuse to write a position until one had been restored, and set that flag in `tryRestore` — the function that *injects* `window.__textstackRestoreScroll` into the WebView. Injection is not arrival. The scroll happens a paint later in another JavaScript realm, and until it reports back, the newest position React Native holds is the `scrollY: 0` the page posts on its own `load` event. The gate was wide open across that entire window, so the unmount flush, the background flush and the debounce all had a zero to write. The restore functions were fire-and-forget and returned nothing; the only feedback was the scroll event they caused, which arrives as an ordinary `progress` message indistinguishable from the reader scrolling and is suppressed outright when the delta is under 0.005. There was nothing to wait for.

So the restore now acknowledges itself. Each one carries an id into the WebView and reports back under its own `restored` message with the offset it reached — the same shape the PDF viewer has used since `pdfPersistGate`, which was written after this same class of bug on the other reader: `scrollToPage(page, jumpId)` in, `ackJumpId` out. The two-state predicate becomes a three-phase machine, `awaiting → issued → open`, and `issued` is the state that did not exist before. It has three ways out, and each earns its place: an id-matched acknowledgement (the happy path, and the id is what stops an ack from the chapter just left opening the gate on the chapter just entered); any reported position above zero, which stands in for a lost acknowledgement because wherever the reader is, they are somewhere real — the load event's zero, deliberately, opens nothing; and a four-second settle timeout on a real timer, the same value and the same argument as `PDF_JUMP_SETTLE_MS`, because one injection that never arrives must not silence saving for the rest of the session. Losing the tail of one session is bad; losing every session is worse. "Nothing was saved" still opens the gate immediately — the top of the chapter is where that reader belongs, and treating it otherwise would mean a first read could never be persisted at all.

The percent branch got a function of its own while the ack was being added. It had been a raw string injected from the hook with no counterpart in the page, which is precisely why it had nowhere to report from; both branches now go through the same helper and the same acknowledgement, and the settings-rebuild re-apply reuses it too. One incidental trap worth recording: the reader document is a single TypeScript template literal, so a backtick in a comment inside it ends the string — the first version of this change did exactly that, and `tsc` reported it as a module declaration error two lines away from the real cause.

Not fixed, deliberately: the report also notes ~75px lost on each re-entry, about 0.05% a time. The likely cause is `scrollTo` under-shooting before the document height has settled — the PDF path handles it by checking page dimensions before acking — but a re-application loop is a new source of races bought for a twentieth of a percent. The acknowledgement now carries the achieved offset, so it is at least measurable when it matters.

<a id="2026-08-28-mobile-a-book-screen-re-reads-where-you-got-to"></a>

<a id="2026-08-28-reader-stopped-writing-a-position-before-restoring-one"></a>

## Reader — the mobile reader stopped writing a position before it had restored one — mobile — 2026-08-28

The other half of the same data loss. Routing a reader to the wrong chapter is recoverable; what made it permanent is that the app then saved that wrong place over the right one, with nobody touching the screen. The WebView posts a `progress` message on its own `load` event carrying `scrollY: 0`, and on the mobile reflow path nothing stood between that and the server — `saveProgress` checked `enabled`, `bookKey` and `chapterSlug`, none of which say whether the reader is where they chose to be. A `restoredRef` existed and no writer read it. Two seconds later, a PUT of zero. The same window opened three other ways: any position load slower than the debounce, leaving a book within two seconds of opening it, and backgrounding the app in that gap — the unmount and AppState flushes were equally ungated. Both of this codebase's other readers already had the answer. The PDF viewer has `pdfPersistGate`, written after exactly this bug in its own form; the web reader keeps `restoredFor` as state rather than a ref, precisely so the save-on-open effect can re-run *after* restore, its comment insisting the offset must reflect the restored scroll "not a transient 0". The mobile reflow reader is simply the one that never got it, and now has it, keyed per chapter because moving on starts a new restore and a single boolean would stay open across the boundary. The gate is a pure function in `src/lib` — where mobile's tests can reach it — and a type predicate rather than a boolean, so extracting the check did not cost a duplicate one beside it. Deliberately not a rule against writing a smaller number: going back is something readers do, and the question is *when* a write is trustworthy, not which way the number moved.
<a id="2026-08-28-settings-a-stored-default-stopped-masquerading"></a>

## Settings — a stored default stopped masquerading as a decision, and auto-speak moved to where it is looked for — backend + mobile — 2026-08-28

QA reported the reader's text alignment still defaulting to left, a day after it was changed to centre. Both were true: the default did change, and their device had a stored `reader.settings.v2` blob from before, which the loader spreads over it. The deeper problem is that the two cases are byte-identical in storage — "the reader chose left" and "left was the default when this device first wrote anything" — because every `update` serialised the whole ten-key object, so adjusting the font size froze every other setting at that day's defaults. <a id="2026-08-28-reader-continuing-a-book-stopped-erasing-where-you-got-to"></a>

## Reader — continuing a book stopped erasing where you had got to — mobile — 2026-08-28

Read to 10% of chapter two, leave, press "Continue Reading": the reader opened chapter *one* at the top, and seconds later the server held `scroll:1-dramatis-personae:0`, percent 0. The place was gone. Three reproductions, both entry points. The tester guessed the client was sending a stale `chapterSlug`; **no client sends `chapterSlug` at all.** The server derives it by joining the progress row's `chapterId` to the chapters table — and `chapterId` was the chapter the URL named, while the locator was built from the chapter on screen. The locator is the position and the slug is a projection of a field that stops moving, so the locator now decides — `resumeChapterSlug` reads the slug out of a `scroll:<slug>:<offset>` locator and prefers it, falling back to the stored chapter only when the locator names one that no longer exists (re-parsing renames chapters) or cannot answer at all (a chapterless PDF stores `page:<N>`). That alone repairs rows already written, because their locators were right the whole time. The write side is fixed where the disagreement starts: the id sent with a save is now resolved from the visible chapter's slug, falling back to the route id when the slug names nothing known — a position saved against a slightly stale chapter is worth more than a position not saved. The function also left `pdfResume.ts` for a file that is not named after one format, since living in a PDF-named file is how it came to consider only `page:<N>` locators to begin with.

## AI tools — three ways an agent could state something the data did not say — backend — 2026-08-28

The tutor telling a reader "You keep missing this word" about a card created a minute earlier turned out not to be one bug. One non-truthfulness finding is fixed here too, being a hole in a defence the project had already built deliberately: `get_example_sentence` emitted `bookTitle` unsanitized while `sentence` and the retrieved text beside it were cleaned, and a user-uploaded title is user-controlled text landing in the planner prompt as a tool observation — the sibling tool that sanitizes titles carries a comment saying to treat them as data and never as instructions. <a id="2026-08-25-reader-six-ways-a-reader-lost-their-place-plus-the-estim"></a>

## Reader — six ways a reader lost their place, plus the estimate that was never built — mobile — 2026-08-25

An adversarial audit of the resume path, prompted by the owner: *"the reading process
must be perfect."* It was not. Every item below was confirmed against the code before
it was touched, and the two most damaging were invisible in any log.

**Progress ran backwards, and the lower value was saved.** The WebView reported
`scrollTop / documentHeight`. But infinite scroll appends the next chapter into the
*same* document, and React Native feeds that number to `computeBookProgress()` as the
*within-chapter* fraction. The moment chapter two landed, standing at the end of
chapter one reported `0.5` labelled "chapter one" — the bar visibly dropped, and the
two-second debounce persisted it to the server. With K chapters loaded, the top of
chapter K reported `(K-1)/K`. The number oscillated for the whole session. Progress is
now computed against the current chapter's own bounds, which the script already
tracked in `chapterSlugs` for a different purpose.

**The saved scroll locator had the same flaw in pixels.** It was an absolute offset
across every appended chapter, restored into a document containing that one chapter
alone. Read into chapter two, stop at absolute 12000 — resume clamps to the bottom of
a chapter you had barely started. The reported offset is now chapter-relative; on a
freshly loaded chapter the two agree, so nothing else changed.

**Offline reading saved nothing at all — 100% of the time.** The offline cache keys
chapters by slug and has no server id to give, so it returns `id: ''`. `saveProgress()`
gated on a truthy `chapterId` and deferred to a replay effect gated the same way, which
therefore never ran. Read three chapters on a plane, close the app, lose every one of
them — and the resume card still showing the pre-flight percent. Offline-first is a
stated pillar of this product; this was the one path where progress was guaranteed lost.
The local write no longer depends on the id; only the server PUT does.

**Chapter navigation overwrote the position it had just saved.** The unmount flush
depended on `saveProgress`, so it fired on every chapter change — with the previous
chapter's closure over refs `navigateChapter` had already zeroed, persisting
`percent: 0, locator: scroll:<old-slug>:0`. Until the destination chapter emitted its
first message, the only stored position was "the chapter you just left, at the top".

**`bookPercent` was erased rather than preserved.** Callers pass `undefined` for "I
don't know yet" — true on every save before the chapter list resolves, and every save
while offline, where it never resolves. `setItem` writes the whole record and
`JSON.stringify` drops `undefined`, so the stored value was deleted; the resume card
fell back to the chapter percent and announced **"85% complete" for a book 12% read**.
The code comment claimed the opposite.

**A PDF never resumed.** Chapterless by design, its position is a `page:<N>` locator
with `chapterSlug: null`. Every consumer looked for a slug, found none, and concluded
the book had never been opened: "Start Reading", routed to chapter one, whose start
page is 1, and the precedence rule *chapter beats server resume page* discarded the
saved page. The locator was written correctly and read on no reachable path. The detail
screen now derives the chapter containing the saved page from the `sourceStartPage`
values the extractor already records, and the precedence rule narrows: a saved page
*inside* the chapter being opened wins. That separates the two ways a reader arrives
without needing a flag — picking chapter 7 from the table of contents opens chapter 7;
Continue routes into the chapter holding the saved page and lands on the page.

**The book being read vanished from Continue Reading at the end of every chapter.**
`ReadingProgress.Percent` is a CHAPTER fraction from mobile and a BOOK fraction from
web, so a bare `1.0` is ambiguous — and a chapter fraction hits exactly 1.0 at the
bottom of any chapter. The `>= 1` exclusion read that as "finished". Exclusion now
requires a percent known to be book-wide, and an ambiguous value is clamped for display.
A finished book lingering is a far smaller error than the current book disappearing at
the moment you want to resume it. Canonicalising the column across web, mobile and the
server shelf is the real fix and is a separate cross-platform change.

**Also.** The reader holds the screen awake — the display timeout fired mid-page, in
the one activity this app exists for (guarded require, so a binary without the native
module simply reads on). PDFs allow pinch zoom: the viewer set `user-scalable=no`, and
on a portrait-locked phone a fixed A4 page renders at roughly 6pt with no way to
magnify it. And "time left", advertised in the settings drawer since it shipped and
never implemented, now exists — `estimateTimeLeft()` over chapter word counts and the
per-user words-per-minute the server has been deriving all along at
`GET /me/reading/pace`, which only web ever consumed.

**Tests: 121 mobile + 258 shared.** The progress reporter is extracted from the HTML
string it ships inside and executed against a fake DOM, so the document-versus-chapter
regression is locked at the source rather than one layer away. `progressStorage` had no
tests at all and now has 13. Two existing tests encoded the old, wrong exclusion rule;
they were rewritten to state the new contract and why it differs, not flipped.

<a id="2026-08-21-ai-24-llm-traces-a-day-were-silently-dropped-postgres-c"></a>

## AI — 24 LLM traces a day were silently dropped: Postgres cannot store a NUL — backend — 2026-08-21

Sentry raised errors, which is how this was found at all. Production logs for the last 24 hours held
468 error lines. Grouped, they were four unrelated problems; this is the largest.

```
Npgsql.PostgresException (0x80004005): 22P02: invalid input syntax for type json
  INSERT INTO llm_traces
  fail: TextStack.Ai.Llm.TracingDecorator
```

24 occurrences, on the `distractor` (6) and `tutor.agent` (2) features — both Ollama-backed.

**The cause.** A NUL byte anywhere in a prompt or a model response is serialized by
System.Text.Json as the six-character escape `\u0000`. That is legal JSON by the specification, and
PostgreSQL refuses it. Confirmed directly against the database rather than assumed:

```
ERROR:  unsupported Unicode escape sequence
DETAIL: \u0000 cannot be converted to text.
```

`llm_traces.messages_json` and `tool_calls_json` are `jsonb`, so the insert throws. It throws inside
`TracingDecorator`'s fire-and-forget writer, which catches and logs — so the only symptom was a log
line and a row that never arrived. Book text extracted from PDFs is a plausible source of stray NULs.

**The fix.** `TraceRedactor.StripNul` removes both forms: the raw character, for the plain `text`
columns (SystemPrompt, ResponseText, Error, which Postgres also cannot store a NUL in), and the escape
sequence, for the already-serialized JSON — a raw NUL cannot survive in serializer output, so the
escape is the only form that reaches `jsonb`. `ToolCallsJson` was bypassing redaction entirely and is
now sanitised too.

Five regression tests, one being the end-to-end shape of the production failure on `distractor`. One
of them caught a bug in *itself* first: the "other Unicode escapes must survive" case had been built
by string substitution that accidentally produced a real NUL escape, so it asserted the opposite of
its own name.

**A wrong theory, recorded because the reasoning is reusable.** The first suspect was
`TraceRedactor.Redact` running email and phone regexes over an already-serialized JSON document — text
surgery on structured data, which looks obviously unsafe. It was reproduced against the real
expressions on realistic payloads, including base64 image data from the vision-RAG path, and it turns
out harmless: every replacement lands inside a quoted string value, so the document stays valid. Two
minutes of testing stopped a plausible-sounding wrong fix.

**Three further problems found in the same logs, not fixed here:**

- `Received backend message BindComplete while expecting ReadyForQueryMessage. Please file a bug.` — 9
  occurrences. Npgsql's own wording for protocol desynchronisation, classically a `DbContext` or
  connection used concurrently from two threads. Worth its own investigation.
- `23505` duplicate key on `ix_reading_progresses_user_id_site_id_edition_id` (2) and
  `ix_reading_sessions_user_id_edition_id_started_at` (2) — the same class as the
  [2026-08-07 postmortem](../incidents/2026-08-07-reading-position-lost-23505.md), which was supposed
  to have closed it. Either that fix is partial or a second path has the same race.
- 18 each of `SocketException (125): Operation canceled`, `IOException: Unable to read data from the
  transport connection` and `NpgsqlException: Exception while reading from stream` — one event seen at
  four layers, most likely clients disconnecting mid-query. Probably benign; 18 a day is worth a look.

## Backend — Npgsql was declared 9.0.3 and running 10.0.2 — backend — 2026-08-21

`Directory.Packages.props` pinned `Npgsql` at **9.0.3**. `Npgsql.EntityFrameworkCore.PostgreSQL`
10.0.1 requires **>= 10.0.2**, so NuGet had been quietly resolving upward on every restore. Nothing
was broken, but the manifest did not describe what shipped — and central package management exists
precisely so that it does. Declared version now matches the resolved one.

**Verified against a real database, not just a build.** The API image was rebuilt and the running
container confirmed to carry `Npgsql.dll` 10.0.2 before anything was measured — otherwise the test
run would have exercised the old driver and proved nothing.

- Integration tests: 171 passed, 0 failed. Every one goes over HTTP into the API and through Npgsql
  to Postgres, which is the path that actually ships.
- Unit 1379, Search 20, Extraction 275 — all passing. The search suite is worth naming separately: it
  runs raw SQL through Dapper rather than EF, so it exercises the driver directly.
- Live endpoints returning real rows: `/books`, `/authors`, `/search`. Zero `PostgresException` or
  `NpgsqlException` in fifteen minutes of API logs.

**On the 45 skipped integration tests.** Sixteen skip on `TEST_DB_CONNECTION not set` — they open
their own connection from the test process rather than going through the API. For a *driver* bump
that is exactly the coverage one would want, and it did not run. Reaching the database from the host
would have meant publishing a port in `docker-compose.yml`, which is not a change to make in order to
run a test. The bump is verified through the API path instead, which is the path in production; the

## Security — two packages with high-severity advisories, one of them unused — backend — 2026-08-20

Found by reading a build log while fixing something else. `dotnet build` had been printing NU1903 on
every run, and nobody had looked.

**`System.Security.Cryptography.Xml` 10.0.8 — five advisories, and no code used it.** A direct
`PackageReference` in `Infrastructure.csproj`, pinned centrally, referenced by nothing: no `SignedXml`,
no `EncryptedXml`, no import of the namespace anywhere in `backend/src`. `dotnet nuget why` showed it
as a root of the dependency graph with no parent, so it was not there to raise a transitive version
either. Deleted.

**`Microsoft.OpenApi` 2.0.0 — GHSA-v5pm-xwqc-g5wc, high.** Transitive, pulled by
`Microsoft.AspNetCore.OpenApi` 10.0.8. Circular schema references can terminate OpenAPI parsing;
vulnerable from `2.0.0-preview.11` through `2.7.4`, patched in `2.7.5`. Pinned to 2.7.5, held on the
2.x line for compatibility with AspNetCore.OpenApi 10.x.

The tidier mechanism would have been `CentralPackageTransitivePinningEnabled`, and it was tried first.
It pins *every* transitive package to the central list, which immediately turned the build into NU1109
downgrade errors — and in doing so exposed something worth recording: the central `Npgsql` entry is
**9.0.3**, while `Npgsql.EntityFrameworkCore.PostgreSQL` 10.0.1 requires **>= 10.0.2**. Resolution has
been quietly upgrading it all along. Nothing is broken today, but the declared version is not the
version that runs, and bumping a database driver is not a change to make in passing. Reverted to two
direct references carrying a comment that says they exist only as a security pin.

Result: `NU1903` count from ten to zero, `dotnet build` at 0 errors, 1379 unit tests passing.

**Also in this change**

*The EF startup warnings are silenced, with the reasoning written down.* Ten
`PossibleIncorrectRequiredNavigationWithQueryFilterInteraction` warnings fired on every boot,
production included: `Edition`, `Author` and `SsgRebuildJob` carry the site query filter and are the
required end of relationships with `BookAsset`, `BookFile`, `Chapter`, `ChapterChunk`, `EditionAuthor`,
`IngestionJob`, `LintResult`, `PodcastGenerationJob` and `SsgRebuildResult`. The hazard EF describes —
a required principal filtered away, leaving dependents pointing at nothing — cannot occur here: the
filter is `x.SiteId == _currentSite.Id` and ADR-007 fixes the deployment to one site with one
`DefaultSiteId`, so it excludes no row that exists. Silenced rather than restructured, because ten
lines of unactionable warning at every boot is how a real warning goes unread. The comment says to
delete the suppression first if multi-site ever returns.

*E2E preconditions now name themselves.* `getTestData()` typed `enBook` as required while
`global-setup` may write `{ siteId: '' }` — so the type lied and the first test to touch it died on
"Cannot read properties of undefined (reading 'slug')". It now throws an error that explains that
global-setup *discovers* books via `GET /books?limit=20` rather than creating them. `fetchBookDetail`
stopped swallowing failures in a bare `catch {}` that became an empty chapter slug and sent reader
tests to a URL with a missing segment. Same family as every other defect found today: a silent
fallback converting a clear precondition into a confusing error several steps downstream.

*Worker logs are captured when E2E fails.* The dump ran `docker compose logs api migrator`. Ingestion
happens in the worker, so when an ingestion-dependent test timed out, the one log that could have
explained it was the one not collected.

*The last two unreferenced EPUB fixtures went.* `test-book-en.epub` and `test-book-uk.epub` had no
consumer, exactly like `test-book-images.epub` deleted alongside the E2E cut. Keeping them would have
been inconsistent with the reason the third one went.

same page pointed at `/en/privacy/`. Not a typo — the banner already used `LocalizedLink`. The cause is
structural: `CookieBanner` is mounted as a sibling of the routes, because it has to appear on `/` too
and `LanguageProvider` only exists inside `/:lang/*`. So `useLanguage()` returned the *default context
value*, whose `getLocalizedPath` was the identity function `(path) => path`.

An identity fallback looks harmless and is not: it silently produces a wrong link for every consumer
rendered outside the provider, and a consent banner — the one component guaranteed to render before any
language route — is exactly where the privacy link has to work. The path-building logic now lives in
`buildLocalizedPath`, shared by the provider and the default value, so the fallback prefixes the default
language instead of returning the path untouched. Four tests cover prefixing, double-prefix avoidance,
query-string handling and missing leading slashes.

**Two admin E2E tests had been skipping on every CI run.** `reader-images.spec.ts` calls `adminLogin`
in `beforeAll` and sets `adminAvailable = false` on failure; CI wrote `ADMIN_EMAIL` and `ADMIN_PASSWORD`
into `.env` but nothing ever *created* that account, so the login 401'd and both tests skipped. A skip
still reports green, so the suite looked healthy while the coverage did not exist. The spec's own
comment — "skip all tests if admin not available (e.g. CI)" — shows the hole was known and accepted.

The E2E job now runs `docker compose exec -T api dotnet Api.dll create-admin` after the API reports
healthy. The CLI catches "already exists" and exits 0, so a warm volume does not fail the job.

**The two URLs Google Play holds had no E2E coverage at all.** The delete-account page had assertions
only because someone happened to write them; `/en/privacy` had none. Both are submitted to the store —
the policy is a listing field, the deletion page satisfies the account-deletion requirement — so if
either stops resolving, the listing breaks and nothing else would say so. Both are now in the `@smoke`
gate, checking wiring only: the page exists and rendered its heading. What it *says* stays covered by
the locale parity test, which is the right layer for content.

Smoke is 7 tests now, the non-blocking half still 45.

**Two entries went to `docs/STATUS.md` rather than to code.** Play's Data Safety form still holds the
answers from before the policy rewrite and now contradicts it — the corrected answers are recorded in
the release runbook, but submitting them is a manual Play Console step, and a form that disagrees with
the policy is the worst of the three possible states. And `llm_traces` grows without bound: that is now
a decision rather than an oversight, since the policy says so plainly and account deletion anonymises
rather than deletes, but the table holds prompts and book excerpts, has no cleanup job, and this project
has already lost a night to disk exhaustion.

Verified: 737 web unit tests pass, `tsc -b` clean, and the banner's link reads `/en/privacy/` in a
browser against a production build.

<a id="2026-08-20-mobile-crash-reporting-wired-but-dormant-until-a-dsn-is-s"></a>

## Mobile — crash reporting, wired but dormant until a DSN is supplied — mobile — 2026-08-20

Until now a JS crash on a tester's device produced a fallback screen and a `console.error` that
reached nobody. `ErrorBoundary.componentDidCatch` logged and stopped there; Play Console reports
native crashes and ANRs but never sees a caught React error; and `src/lib/analytics.ts` is a complete
184-line event taxonomy wired to nothing. Entering a 14-day closed test in that state means a tester
says "it crashed" and there is no way to find out why.

Sentry rather than Crashlytics, and it was not close. The backend already runs Sentry across API and
Worker with LLM and provider-routing spans, so mobile joins the same issue stream, and a Book Chat
failure can become one trace from tap to OpenAI call instead of two unrelated haystacks. Crashlytics
would have dragged in Firebase, a `google-services.json` and the Advertising ID question, for a
strictly worse Data Safety posture and a second observability vendor.

**Dormant by default, on the backend's contract.** No `EXPO_PUBLIC_SENTRY_DSN`, no SDK: `initSentry()`
returns immediately and the app behaves exactly as before. Worth knowing the mechanic — Expo *inlines*
`EXPO_PUBLIC_*` at bundle time, so the DSN is baked in when the build or `eas update` runs rather than
read at launch. Confirmed by inspecting the exported bundle: Sentry is present, and the DSN branch has
been compiled away.

**A trap found by building it.** Adding the Sentry Expo plugin made the Gradle release task exit 1:
`sentry-cli` runs during the build to upload source maps and fails outright when `SENTRY_AUTH_TOKEN`
is absent. Left as-is, the owner's next EAS build would have broken on a missing secret with a
confusing error. The plugin now sets `disableAutoUpload: true`, and the runbook says to flip it in the
same change that adds the secret — because without uploads every production stack trace is minified
Hermes bytecode offsets and the integration is decorative. Both switches, one change.

**Scrubbing, because of what this app is.** People read copyrighted and personal books here. A
breadcrumb that innocently records a TTS or translate call carries the passage being read, and
`/api/tts`, `/api/translate` and `/api/explain` all take that text as a query parameter — so the
default behaviour would ship book content to a processor we have not disclosed. `sentryScrub.ts`
redacts `text`, `q`, `word`, `sentence`, `prompt` and `question` from every breadcrumb and request URL
while leaving `page` and `sort` intact, so URLs stay debuggable. Seven tests cover it.

It lives in its own module importing nothing, for a reason worth recording: importing
`@sentry/react-native` into a test pulls in React Native's Flow-typed sources and the transformer dies
with `Expected 'from', got 'typeOf'`. Splitting the rules from the SDK wiring made them testable and
is better design anyway — the rules are the part with decisions in them.

**Also configured:** `dist` from `Updates.updateId`, so "crashing on build 21" and "crashing on
Tuesday's OTA" are distinguishable — without it a JS-only fix looks like it changed nothing.
`sendDefaultPii: false`, no `Sentry.setUser`, no Session Replay: crash data stays in the *not linked
to identity* bucket on the Data Safety form. `Sentry.wrap` on the root layout for touch and navigation
breadcrumbs, and `initSentry()` before provider setup so a failure during startup is still reported.

Verified: `expo prebuild` applies the plugin under SDK 55, the Gradle release manifest task exits 0,
the permission guard still reports 37 permissions with none unsanctioned (Sentry adds none), the
Android bundle exports cleanly at 8.9 MB, `tsc --noEmit` is clean, and 90 unit tests pass.

Turning it on is two owner steps, documented in `docs/03-ops/play-store-release.md`: create a
`textstack-mobile` Sentry project for the DSN, and add `SENTRY_AUTH_TOKEN` as an EAS secret.

<a id="2026-08-20-ci-e2e-stops-gating-production-on-everything-except-smok"></a>

## CI — E2E stops gating production on everything except smoke, and the Chrome download stops flaking deploys — infra — 2026-08-20

Prompted by a fair question — *do we actually need these tests?* — and answered with the repository's
own record rather than with principle.

**What the record says.** 20 of the 70 commits touching `apps/web/e2e` were about flakes, timeouts and
waits: a third of the suite's maintenance went into keeping the suite running. And the one production
incident inside its strongest coverage area — reading position lost to a 23505 upsert race on
2026-08-07, with 13 of 47 tests devoted to progress and bookmarks — was caught by Sentry, not by these
tests. The postmortem is blunt about it: *"Sentry, within hours… This is the incident that paid for the
integration."* A single-threaded Playwright script cannot produce a concurrent write, so that class of
bug was never within reach. The five-week SSG outage was found by a screenshot.

Set against that, the suite does earn something real: it catches broken *wiring*. On this very day it
caught a rewrite of the delete-account page that had silently dropped "This action cannot be undone." —
the one sentence stating irreversibility, on the page a Play reviewer reads.

So the verdict is neither "delete" nor "keep": the shallow part is worth gating on, the deep part is
worth reading but not worth blocking a release for.

**The split.** `smoke.spec.ts` is tagged `@smoke` and gates the deploy — 5 tests: the home page renders,
the catalog lists books, search resolves, an unknown route 404s, the API answers. Cheap, deterministic,
and about wiring only; nothing needing a fixture, a login or a timing assumption belongs in it. The
other 45 run in the same job with `continue-on-error: true`, and a failure raises a workflow warning
plus a job-summary note instead of stopping a release. The Playwright report now uploads on `always()`
rather than `failure()`, since a non-blocking failure no longer fails the job.

**Not done, on inspection.** The plan had been to run the full suite nightly against production. Reading
`global-setup.ts` and the specs killed that: setup uploads test books, and six specs mutate — including
`delete-account.spec.ts`, which deletes accounts. Pointing that at production would create and destroy
real records. And with the full suite already running non-blocking on every PR and every deploy, a
nightly run against an ephemeral stack would mostly re-confirm the same result. Dropped rather than
built.

**The flake that started it.** The deploy that carried the privacy policy was blocked not by a test but
by `storage.googleapis.com` returning 504 while the worker image downloaded Chrome for puppeteer. The
existing guard was three attempts five seconds apart — about fifteen seconds of cover — and all three
burned inside the outage.

Now the npm install and the browser download are separate steps, because they fail for unrelated
reasons at unrelated rates: the install talks to the npm registry and is quick, the download pulls
~150 MB from Google and is the part that flakes. The install runs with `PUPPETEER_SKIP_DOWNLOAD=true`,
and the download retries five times with exponential backoff — 10s, 20s, 40s, 80s, 160s, roughly five
minutes of cover.

One trap avoided along the way. The obvious retry command is
`npx puppeteer browsers install chrome-headless-shell`, since that is what the error named. It would
have been wrong: puppeteer 24 downloads **both** `chrome` and `chrome-headless-shell`, and
`prerender.mjs` calls `launch({ headless: true })`, which resolves to full `chrome` —
`chrome-headless-shell` is only used for `headless: 'shell'`. Installing just the shell would have
produced an image whose SSG could not launch a browser at all: precisely the silent failure that kept
SSG dead for five weeks. The retry therefore wraps puppeteer's own installer, the exact code path that
failed, and the build now asserts `chrome/` exists in the cache rather than merely that the directory
is non-empty.

Verified by building the worker image: both browsers download into `PUPPETEER_CACHE_DIR`, and the guard
passes. Launching Chrome inside the image fails locally with a rosetta error because this is an arm64
Mac and Chrome for Testing ships x86-64 binaries — the same arm64-vs-prod mismatch already documented
for the worker. The downloaded artifacts are identical to before by construction, since the retry
invokes the same `install.mjs` that `npm install` ran as its postinstall.

<a id="2026-08-20-legal-the-privacy-policy-said-data-stayed-in-your-browse"></a>

## Legal — the privacy policy said data stayed in your browser and that nothing was shared; both were false — web + mobile — 2026-08-20

The policy that shipped to Google Play with the internal-testing release contained two claims that
were not merely outdated but the opposite of what the product does:

> "If you choose to use optional features like saving reading progress or bookmarks, this data is
> stored **locally in your browser**."

> "We do not sell, rent, or **share** your personal information with third parties."

Reading progress, highlights, vocabulary and uploaded books are stored server-side and linked to an
account. And book text goes to OpenAI on every AI feature; text goes to Microsoft for speech; looked-up
words go to dictionaryapi.dev; sign-in goes to Google and Apple; email goes to Resend; server errors go
to Sentry; and the website loads Google Analytics and Ahrefs after consent. `CLAUDE.md` even recorded
that the Free Dictionary API was dropped from the mobile reader specifically "to shrink the Play Store
Data Safety third-party processor list to OpenAI + Edge TTS only" — so the list was known internally
and simply never disclosed. It was dated "January 2025", as were the Terms.

A Data Safety declaration that contradicts the policy is a suspension category, not a warning
category, and both had already been submitted.

**What the rewrite says.** Fourteen sections, each mapped to a row that can actually be ticked on the
Data Safety form: scope (site *and* apps); what is collected, split into account, uploaded content,
reading activity, AI interaction data, technical data, and the genuinely device-only preferences; why;
who receives it, naming all nine processors one by one; a section on the AI features; cookies and the
consent gate; storage and security; retention; rights and both deletion routes; children; international
transfers; changes.

Two answers are worth stating plainly because they were the hard ones.

*Sharing.* Sending book text to OpenAI is "sharing" under Play's definition — Files & docs → Shared:
Yes. That is the row most often got wrong, and it is now what both the policy and the form say. The
honest replacement for the old blanket claim is narrower and defensible: we do not sell personal
information and do not share it with advertisers or data brokers.

*Retention.* `LlmTrace` stores `SystemPrompt`, `MessagesJson` and `ResponseText` with a `UserId` — your
prompts and the book excerpts sent as context — and there is no cleanup job anywhere in the backend.
Rather than promise a deletion schedule nobody would run, the policy says what is true: AI interaction
records are kept indefinitely as the operational record of what the service did and what it cost, and
account deletion severs the link (`ON DELETE SET NULL`) so what remains is anonymous. An ugly number
you enforce beats a pretty one you do not.

**Structural fix, so it cannot rot the same way.** Both the web page and the mobile screen used to
hardcode their own sequence of `t()` calls, so adding a section meant editing four files and
remembering all four — which is precisely how one copy of the truth got left behind. The order now
lives in `packages/shared/src/legal/sections.ts` and both clients map over it.

`apps/web/src/locales/__tests__/legalParity.test.ts` holds the line: the `privacy.*` and `terms.*`
blocks must be value-for-value identical between the web locale file and the shared one (Play requires
the in-app policy and the policy at the listed URL to match), every key the section list references
must exist in both, all seven processors must still be named, the retention answer must still be
stated, and the two false sentences must not come back.

That parity check immediately found that Terms had *already* drifted: the mobile copy was missing the
uploads warranty, the indemnity, the DMCA route and the liability cap — seven keys and ten reworded
paragraphs behind the web version, for months, on the platform where users upload books. Mobile now
renders all of it, with the DMCA process linked from both the Terms screen and the profile menu, since
rights holders need a route to it from inside the app that hosts the uploads.

**Delete-account page.** It told a Play reviewer to "open the user menu in the top-right corner" —
the *web* UI. A reviewer opening that URL on Android would go looking for a control that does not exist
there. It now gives both paths separately, and states the timing: deletion is immediate, in one
transaction, with no waiting period and no recovery window.

**Terms** gained an AI section (output is generated, not verified; using the features sends your
selection and its surrounding passage to our providers; how to report a bad response) and a real date.

**Runbook.** `docs/03-ops/play-store-release.md` is new — there was no mobile release runbook at all.
It carries the submitted Data Safety answers verbatim, because Play offers no export and they will be
needed at every future update; the track↔profile mapping; the staged-rollout ladder and the fact that
EAS cannot advance an existing rollout; the fingerprint rule that a native-dependency change needs a
build and not an OTA; and the permission allowlist with its two unresolved WATCH groups.

Verified in a browser, not only by types: all fourteen sections render on the web policy page with the
deletion link live, Terms renders the new AI section without breaking the surrounding markup, and the
delete-account page shows both platform paths. 733 web tests and 83 mobile tests pass.

<a id="2026-08-20-mobile-a-farewell-banner-for-the-frozen-100-runtime-befor"></a>

## Mobile — a farewell banner for the frozen `1.0.0` runtime, before the fingerprint switch strands it — mobile — 2026-08-20

`app.json` set `runtimeVersion.policy: "appVersion"`, which resolves to the literal string `1.0.0`,
while `eas.json` `autoIncrement` bumps only `versionCode`. Every native build ever made therefore
reports the same runtime, and any OTA published to it can land on a binary that lacks the native
modules that update needs. This is not hypothetical: the defensive `try { require(...) } catch {}`
blocks in `useTts.ts:158`, `vocabReminder.ts:41` and `profile.tsx:7` exist for exactly this, and they
degrade features in silence rather than crashing — which is why it has not blown up yet, and why it
would not announce itself when it did.

The fix is `runtimeVersion.policy: "fingerprint"`, which hashes the native inputs — config plugins,
native dependencies, `app.json` — so adding a native module changes the runtime *by construction*
instead of by someone remembering to bump a version string. Discipline you have to remember is not a
fix.

The switch has one cost that cannot be engineered away, only made visible: afterwards, no `eas update`
can ever target `1.0.0` again. Anyone still on an old binary stops receiving updates forever, and
nothing tells them. A silent OTA freeze.

So this is the last thing published to that runtime — a farewell OTA carrying a banner: *this version
no longer receives updates, install the latest from Google Play*. It turns an invisible freeze into a
prompt with a button.

**Order matters, and cannot be compressed.** Publish this to the old runtime *before* the policy
change merges:

```
npx eas update --branch production --platform android \
  --message "Update available from Play Store"
```

Then land the permission/plugin work (it changes the fingerprint), then flip the policy, then build.

**Self-disabling by design.** The gate is `isLegacyRuntime()` in `src/lib/legacyRuntime.ts`: true only
for an updates-enabled Android build reporting exactly `1.0.0`. Builds made after the switch carry a
fingerprint hash, so it renders null on them — the banner is safe to leave in the tree permanently and
costs one string comparison at mount. Expo Go and dev clients report `isEnabled === false` and never
see it. iOS is excluded: the farewell OTA is Android-only and there is no iOS listing to send anyone
to.

The predicate lives in `lib/` rather than inside the component so it is covered by mobile's test
include (`src/lib/**/*.test.ts`). Five tests, because being wrong is expensive in both directions:
too loose and every user on a current build is told to update to the build they already have; too
tight and the stranded users never hear about it, which is the exact silence the banner exists to
break.

A static import of `expo-updates` is safe here even though the codebase guards other native modules
defensively — an OTA is *delivered by* expo-updates, so any build that can receive this code
necessarily has it.

Also in this change: `/slice` deleted. It read a `PLAYBOOK-ai-portfolio.md` that has never existed in
git, and the AI-portfolio phases it was written for are complete. It had also drifted into meaning two
different things — the command file pointed at that playbook, while `.claude/commands/README.md`
documented it as reading UX roadmap briefs. Five dangling references cleaned up with it, including one
in `product-manager.md` that pointed at two more files that do not exist. Note that
`docs/ux-roadmap-v3/` is live (6 slices); the workflow there is now to point Claude at the brief file
directly.

<a id="2026-08-19-reader-the-dyslexic-font-was-a-saved-github-web-page-on-bot"></a>

## Reader — the dyslexic font was a saved GitHub web page on both platforms, so the setting never worked — web + mobile — 2026-08-19

`apps/web/public/fonts/OpenDyslexic-Regular.woff2` was 297,194 bytes that began with eight newlines
and then `<!DOCTYPE html><html lang="en" data-color-mode="auto"...`. It was a GitHub page, curl'd and
saved with a `.woff2` extension. `reader.css` declared it as a real `@font-face`, the browser failed
to parse it, and the "Dyslexic" reader font fell back to sans-serif — no console error, no failed
request, nothing to notice.

The mobile app inherited it by value. `apps/mobile/src/lib/openDyslexicBase64.ts` held 396 KB of
base64 of *those same bytes*, inlined into the WebView reader's `@font-face` by `readerHtml.ts`. The
decoded payload was byte-for-byte the same HTML page. So the accessibility setting had never worked
on either platform, and the mobile JS bundle carried 396 KB of a web page to achieve it.

Both now ship the real font: OpenDyslexic Regular from `@fontsource/opendyslexic` 5.3.0, SIL Open
Font License 1.1, 115,280 bytes, beginning with the `wOF2` signature. The licence text sits next to
it at `apps/web/public/fonts/OpenDyslexic-LICENSE.txt`. The mobile blob is regenerated *from* the web
file by `npm run build:dyslexic-font`, so the two platforms cannot drift apart — or, as here, ship
the same wrong thing twice. It went from 396 KB to 154 KB and started working.

Removing the feature was the other option and the cheaper one. It lost on the grounds that an
accessibility setting which silently does nothing is worse than one that is absent, and fixing it
properly turned out to cost about the same.

**Why nothing caught it for months.** A font is a static asset. No unit test opens `public/`, no
build step validates that a file with a font extension is a font, and a failed `@font-face` degrades
silently by design — that is what a fallback stack is *for*. The failure mode had no output at all.

So there are now two tests that go looking, one per platform:
`apps/web/src/styles/__tests__/fonts.test.ts` reads every file under `public/fonts` and asserts the
`wOF2` signature; `apps/mobile/src/lib/openDyslexicBase64.test.ts` decodes the base64 and asserts the
same, plus that it is not an HTML document and that its size is plausible for a font. The generator
script refuses to run against a source file that is not a woff2. Three checks, because the original
mistake was made once and then copied.

## CI — web unit tests and the whole mobile app were never checked by CI — infra — 2026-08-19

Two gaps found while wiring the font regression tests above, both of the same shape: a test suite
exists, passes, and was never run by anything except a human remembering to.

**The web suite was never in CI.** The `frontend` job ran `pnpm install && pnpm build` for web and
admin and stopped. 100 test files and 731 assertions, invisible to every pull request. A failing web
unit test merged to `main` unnoticed. It now runs `pnpm test` between the build and the overlay
drift-check. All 731 pass today, so this changes nothing about the current tree — it changes what
happens to the next regression.

**The mobile app had no job at all.** `apps/mobile` appeared in `ci.yml` exactly once, as
`pnpm check:mobile-overlay` — a drift check on a generated bundle, run from the *web* working
directory. No `tsc --noEmit`, no unit tests. A mobile type error reached `main` unnoticed, which is
an uncomfortable thing to be true of an app about to go to strangers on a closed track.

There is now a `mobile` job: `npm ci`, `npm run typecheck`, `npm test`. It is a separate job rather
than another step in `frontend` because `apps/mobile` uses npm and its own lockfile, not the pnpm
workspace. `@textstack/shared` is consumed from source through Metro `watchFolders` and tsconfig
paths, so the checkout already carries it and only the app's own dependencies need installing.

Deliberately not included: mobile e2e. `apps/mobile/e2e` is Playwright driving the Expo *web* build
in a Pixel-sized viewport. It exercises no native code path, so running it in CI would buy confidence
it cannot actually provide. (It is also 6 specs, not the 15–16 the docs claim — a separate correction.)

**Turning the web suite on immediately found something.** `readerOverlayMobileBundle.test.ts` lived in
`apps/web/src/lib/` and imported the mobile bundle across the app boundary as
`../../../mobile/src/lib/readerOverlayScript.generated`. That passes on a laptop where someone has
run `npm install` in `apps/mobile` at some point. In CI it failed on the first run: resolving a `.ts`
file under `apps/mobile` makes Vite parse `apps/mobile/tsconfig.json`, which extends
`expo/tsconfig.base` — a module the frontend job never installs, because mobile is npm with its own
lockfile and its own job.

The fix was to move the test rather than install mobile's dependencies twice. It tests a mobile
artifact; it now lives in `apps/mobile/src/lib/` and runs in the mobile job, opting into jsdom with a
`// @vitest-environment jsdom` docblock (mobile's vitest config already supported that — it just
needed `jsdom` as a devDependency). Web is down to 99 files / 726 tests, mobile up to 8 / 78: the
same five assertions, on the correct side of the boundary, and web no longer imports from
`apps/mobile` at all.

Which is the ordinary yield of switching on a check that was never on. The first thing it tells you
is something that was already true.

<a id="2026-08-19-mobile-play-production-plumbing-a-submit-profile-that-exi"></a>

## Mobile — Play production plumbing: a submit profile that exists, two permissions that shouldn't, and a guard — mobile + infra — 2026-08-19

Three things stood between the Android app and a production submission, and none of them were
visible from the source tree alone.

**A submit profile that did not exist.** `eas.json` had `submit.internal` and `submit.closed`, and
`package.json` had `submit:ios` / `submit:android` scripts pointing at a `production` profile that
was never written. Both scripts had been dead since they were added. There is now a real
`submit.production` at a 10% staged rollout — `releaseStatus: inProgress` plus `rollout: 0.1`, a
fraction and not a percentage, which is the mistake this note exists to prevent. EAS cannot advance
an existing rollout, so 10 → 25 → 50 → 100 stays a Play Console action; re-submitting with a larger
number creates a second release instead of widening the first. Scripts are now named after the track
they ship to: `submit:internal`, `submit:closed`, `submit:production`.

**Two permissions that were never ours.** The app requested `RECORD_AUDIO` and
`SYSTEM_ALERT_WINDOW`, and had done so through every internal-testing build. Neither has a feature
behind it: TTS only plays audio back (`useTts.ts` sets `allowsRecording: false`), and the image
picker is avatar-only. `RECORD_AUDIO` comes from the `expo-audio` / `expo-image-picker` config
plugins. `SYSTEM_ALERT_WINDOW` comes from `expo-dev-launcher` — whose *native module* is
debug-gated, but whose *config plugin* runs at prebuild and writes into the shared main manifest, so
it lands in release builds too. Moving `expo-dev-client` around would not have fixed it.

Both are blocked now, along with `CAMERA`, using two mechanisms on purpose. The plugin props
(`microphonePermission: false`, `cameraPermission: false`) state the intent and reliably suppress the
iOS usage strings; `android.blockedPermissions` emits `tools:node="remove"` and is what the manifest
merger actually honours even if a transitive AAR reintroduces the permission.

**The verification is the interesting part.** `tools:node="remove"` in a source manifest is a
directive, not a result, so the fix was checked against the merged release manifest produced by
`./gradlew :app:processReleaseMainManifest`. All three permissions are absent there.

That merge also exposed how little the source manifest was telling us. The source lists 10
permissions; the merge produces 37. Everything the libraries contribute — `POST_NOTIFICATIONS`,
`WAKE_LOCK`, `RECEIVE_BOOT_COMPLETED`, `USE_BIOMETRIC`, the FCM receive permission — is invisible
until the merger runs, and it is the merged set that Play shows a user.

So `scripts/check-android-permissions.mjs` reads the merged manifest when one exists and falls back
to the source with a warning. It fails the build on any permission not explicitly listed with a
written reason. It was tested in both directions before being trusted: it fails on the pre-fix
manifest, fails again on an injected `READ_CONTACTS`, and passes on the fixed one. A guard nobody has
watched fail is not a guard.

**What the guard found that the audit had not.** 22 permissions are on a WATCH list — reported on
every run, deliberately not blocked yet:

- `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, injected unconditionally by
  `expo-audio`. This app plays TTS in the foreground only — no `UIBackgroundModes`, no media
  service — so they look unused, and `MEDIA_PLAYBACK` is not free: it pulls the app into Play's
  foreground-service declaration flow, which wants a form and a demo video. They are not blocked
  blind, because if `expo-audio` starts a service internally then blocking them turns TTS into a
  `SecurityException`, and TTS is a core feature. That needs a device, not a guess.
- 20 OEM launcher and badge permissions from ShortcutBadger, pulled in transitively by
  `expo-notifications` — Samsung, Huawei, Oppo, HTC, Sony, and friends. The app never sets a badge

<a id="2026-08-11-seo-static-site-generation-had-been-dead-for-five-weeks-a-fo"></a>

## SEO — static-site generation had been dead for five weeks; a forbidden HTTP header killed it — backend — 2026-08-11

> Postmortem: [`docs/incidents/2026-08-11-ssg-dead-five-weeks.md`](../incidents/2026-08-11-ssg-dead-five-weeks.md)

Started from a Bing Webmaster Tools screenshot with four warnings and ended somewhere else entirely. The warnings ("limited crawl capacity", "too many pages with insufficient content") were symptoms; Google Search Console independently agreed (`Crawled – currently not indexed: 780`, `Discovered – not indexed: 311`, `Soft 404: 67` with a validation started 15 May that never passed). Chasing the soft-404 list led to real book and author pages — Pan Michael, The Wings of the Dove, Lew Wallace — not the junk URLs an initial guess predicted.

**Root cause.** `ssg-worker.mjs` calls `http://api:8080/ssg/routes` and deliberately sets a `Host` header so `SiteContextMiddleware` can resolve the site — the file even carries a comment explaining that without it "fetch would otherwise default Host to the URL host (`api`) → 404 → silent job". That mitigation cannot work: **`Host` is a forbidden header name in the fetch spec**, so undici drops it. Verified inside the running container — `fetch` with an explicit `Host: textstack.app` still returns 404. The request arrives as `Host: api`, which is not in `site_domains`, so resolution returned null and the middleware answered `404 Site not found`. Every rebuild job failed. The worker stayed `healthy`, and the only evidence was a log line nobody was watching.

The trigger was refactor R1b, which removed the legacy `?site=` override that had been papering over this.

**Blast radius, measured.** Newest generated page: **3 July**. The sitemap is built live from the database and advertises **1153** book URLs; the generator had produced **764** pages. So roughly **389 published books returned a hard 404 to crawlers** while being actively advertised in the sitemap — which is precisely Google's `Not found (404): 153` and Bing's 140-of-1.3K index.

**Fix.** `SiteResolver` now falls back to the single site (`ICurrentSite.Id`) when the host matches no registered domain, logging a warning naming the host. This is safe in exactly the way the removed `?site=` override was not: that override could name a *different* site, producing a `SiteContext` whose Id diverged from the process-wide `ICurrentSite.Id` that EF's global query filters key on — silently yielding zero rows. Resolving to `ICurrentSite.Id` itself makes divergence impossible, and which hosts can reach the middleware at all is already constrained by `AllowedHosts`. Fixing the resolver rather than the worker also closes the class: any future internal caller that cannot set `Host` (which is every `fetch` caller) now works.

Covered by integration tests rather than unit tests, deliberately: `SiteResolver` depends on the concrete `AppDbContext`, whose model only builds on Npgsql, and the failure was inherently about a real request's host — something a mock cannot express. `SsgRouteResolutionTests` asserts `/ssg/routes` returns 200 for `Host: api`, still works for a known host, and returns a non-empty route list (an empty list would rebuild nothing while reporting success — the same silent-failure shape).

**Two pieces of misleading infrastructure found on the way, worth knowing even though they are not the bug.** `X-SEO-Render` is set from `map $is_bot`, so it reports "you look like a bot", NOT "an SSG file was served" — it says `ssg` even when the fallback ran, which cost real debugging time here. And nginx's `location /ssg/ { internal; alias …/data/ssg/; }` points at a directory that does not exist; `try_files` resolves `$ssg_file` against `root` instead, so the real pages come from `apps/web/dist/ssg` and that block is dead code whose comment asserts it is required.

**This fix alone does not restore the pages** — a full SSG rebuild has to run after deploy for those ~389 books to get generated.

Not addressed here, and separate: the catch-all `location /` returns 200 to bots for any non-SSG path (the bot-404 guard exists only in `@spa`), and Cloudflare's managed `robots.txt` block sets `Content-Signal: ai-input` absent plus `Disallow: /` for ClaudeBot/GPTBot/Google-Extended and friends, which is why Bing reports the site cannot appear in Copilot and grounding results. The latter is a product decision, not a bug.

<a id="2026-08-09-users-entitlement-tiers-replace-two-hardcoded-storage-consta"></a>

## Users — entitlement tiers replace two hardcoded storage constants — backend — 2026-08-09

Triggered by a support case that turned out to be two unrelated ceilings wearing one error message. An upload failed with `Upload failed: 413` while the quota bar read 167.7 MB of 500 MB — plenty of room. **The 413 is Cloudflare's per-request body cap, not our quota**, verified against production by probing with increasing bodies: 10/50/90 MB reached the API (401 — the body got through), 110 MB returned `413 cloudflare`. nginx and Kestrel are both already configured at 500 MB and were never the constraint. That half is fixed separately by chunked upload; this entry is the other half.

The other half: storage limits were two `const`s on `User` (`StorageLimitBytes = 500MB`, `GuestStorageLimitBytes = 50MB`) read through a `user.IsGuest ? … : …` ternary duplicated at the two enforcement sites, and `IsGuest` was the **entire** user taxonomy — `User` has no role column, and `AdminUser` is a completely disjoint table with its own auth, own tokens and no foreign key to `User`. So "give the owner's account 5 GB" was not expressible at all, and neither was any future paid tier.

Introduces `UserTier { Guest, Free, Supporter, Staff }` as a **string** column (house style for new enum columns — readable in psql, immune to renumbering) plus a nullable `storage_limit_override_bytes` for genuine one-offs. Limits themselves live in the new `Entitlements` config section, not in code, so changing a quota is a config edit rather than a deploy: **Guest 50 MB · Free 500 MB · Supporter 2 GB · Staff 5 GB**. The options type deliberately mirrors `BudgetOptions` — root record with `Default` + a dictionary, static `Empty`, accessor-per-field normalizing its own "absent" sentinel, partial inheritance in `Lookup`, pure and never-throws — because that shape already solved this exact problem here and is unit-tested standalone. The binder is the same hand-rolled `AddSingleton` factory: an unknown tier key is skipped rather than thrown, so a typo degrades to the default instead of failing startup.

**The migration backfills `tier = 'Guest'` for existing guests.** The column default is `Free`, which is right for every registered account and wrong for guests — without the backfill, every existing guest would have silently jumped from a 50 MB to a 500 MB allowance the moment this deployed.

Three decisions worth recording. **Staff is granted by `Entitlements:StaffEmails`, not an admin endpoint** — there is no CRUD over site `User` anywhere in the admin app today, and building a management console for a population of one to three is the wrong trade; the config list is reviewable in git, needs no DB write and no new auth surface, and the column remains as a documented manual escape hatch. **The grant is fail-closed for guests**: if `IsGuest`, the allowlist is not consulted at all, because guest emails are synthesized (`guest-{guid}@guest.local`) and one collision must not be able to mint an anonymous 5 GB session. **`MaxSingleUploadBytes` lives on the root options record, not on `TierEntitlements`** — it is Cloudflare's ceiling, not a perk, so "Staff may upload bigger files" is *structurally* inexpressible (there is no key to put it under) and the binder additionally clamps it to a compiled-in platform constant. A test asserts guest and staff receive the identical value.

Two defects the tests caught in this change itself, both fixed. Staff-email normalization initially lived in the DI binder rather than in the options type, so a config entry with a trailing space or a capitalized domain would silently fail to match — and the failure mode (staff quietly not recognized) is invisible; a guarantee outside the type is not a guarantee, since tests and any other construction path bypass it, so it moved into the record. And `GetStorageQuotaAsync` initially kept a separate branch for "user not found", which could drift from what an upload actually enforces; both paths now go through the one resolver, so the quota endpoint cannot disagree with reality.

Also deleted rather than migrated: the `FileUpload:{MaxBookSizeMb,MaxCoverSizeMb,MaxPhotoSizeMb}` config block, which had **zero readers** while `MaxBookSizeMb: 100` read convincingly like the real limit.

`StorageQuotaDto` gains `Tier`, `MaxBooks`, `BooksUsed` and `MaxSingleUploadBytes` so clients can explain a refusal instead of surfacing a raw status code. **1379 unit tests green** (16 new in `EntitlementResolverTests`, covering the guest fail-closed rule, override clamping, and that a mistyped quota of `0` falls back to a working default rather than locking every user out of uploading). Build and `dotnet format --verify-no-changes` clean.

Not in this change: chunked upload (the actual 413 fix), any billing, and migrating the other per-user caps — vocabulary 5000, collections 50, tags 20, avatar 2 MB, agent cost caps — onto tiers. They are catalogued and deliberately left for later rather than folded into one PR with five new enforcement points.

## Worker — provider readiness check + circuit breaker, and a Sentry environment tag that lied — backend + infra — 2026-08-08

**First, a correction, because this entry exists because of a misread and repeating it would be worse than the bug.** The Sentry issue that prompted this work (`System.Net.Http.HttpRequestException: Name or service not known (ollama:11434)`, 30 events, tagged `environment: Production`) did **not** come from production. It came from a developer machine. Four independent checks: the events report `linux-arm64` (prod is x86_64), release `ee15354c` (a branch commit that was never deployed — prod went `71c6b1da` → `df551f15` → `bb7cfc1c` → `58fec417`), prod's `ollama` container has been `Up 4 weeks (healthy)` with the Worker resolving it to `172.18.0.8`, prod's Worker logged **zero** occurrences of "ollama" in 24 h, and prod has **zero** backfill candidates (`status = Ready AND genre IS NULL`) — every one of its 50 user books has a genre. The "38 starved books" were a local database.

**Why the tag lied, and the fix.** The local `.env` sets `ASPNETCORE_ENVIRONMENT=Production`, so a dev box pointed at the production DSN wrote events into the production Sentry project under a production tag. Anyone reading that UI would conclude "prod", and someone did. `SentryBootstrap.ResolveEnvironmentName` now downgrades a `Production` claim to **`production-unverified`** when `SENTRY_RELEASE` is absent — the release is set from the `GIT_SHA` build arg in both Dockerfiles, so every CI-built image has one and no `dotnet run` ever does. Real production is unaffected. Deliberately a rename rather than a drop: an unverified event is still worth having, it just must not masquerade (filter with `!environment:production-unverified`). `.env.example` gained a warning, and the local `.env` was corrected.

**The hardening stands on its own merits, which are not hypothetical.** Nothing checked provider reachability at startup, so a genuinely dead prod Ollama would fail exactly as silently — `distractor`, `bookmeta`, `tagsuggestion` and every unrouted tag (the Worker's `Ai:DefaultProvider` is `ollama`) degrade quietly. `MetadataBackfillWorker` would spend up to **50 × `Ollama:TimeoutSeconds` (90 s) ≈ 77 minutes** of dead wall-clock per worker start. And worst: `UserBookEnrichmentService.EnrichAsync` stamps **`Completed`, not `Failed`,** when the generator returns null — which is exactly what an unreachable provider produces — so `MetadataEnrichmentWorker`'s 30 s drain would quietly empty the queue into a terminal "done, nothing filled" state that nothing revisits. That last one is provider-independent data loss and was worth the trip on its own.

**What shipped.** `AiProviderReadinessCheck` (replacing `EnrichmentKeyCheck`, whose job it strictly supersedes and whose hardcoded provider set had already drifted — it omitted `openai-pdf`, the most expensive route in the system) probes every provider the route table actually references, once, before any worker loop starts: Ollama via `GET {Ollama:BaseUrl}/api/tags` on a 2 s timeout (the same probe shape the API's `/health/ready` already uses), OpenAI-family by key presence only — **it never spends a token to prove a paid provider is up**. An unreachable provider produces one `LogError` naming the affected tags (`(default), bookmeta, distractor, tagsuggestion → ollama (unreachable)`) plus one Sentry warning, and seeds that provider's circuit open. It can never crash or block the host.

`ProviderCircuitPolicy` is the breaker: pure statics with the clock as a parameter, mirroring `AlarmThrottle` because this repo has no clock abstraction. `OpenedAt` survives escalation, so `JustTripped` is true exactly once per outage — **that single predicate is the whole "one event per condition, not one per retry" requirement**, and it is what turns 30 duplicate events into 1. Backoff 1 → 5 → 30 min (`Ai:ProviderHealth:BackoffMinutes`). Detection lives **inside `OllamaLlmClient`**, beside the three existing `LlmFailureAlarm.Capture` calls, because that is the only place that knows a call died on the wire: the client swallows transport failures and returns an empty response, so a decorator would see success-with-empty and could not distinguish a dead Ollama from a model that said nothing. A **non-2xx deliberately does not trip** — that means Ollama is alive and answering (typically a wrong `Ollama:Model` → 404), fails in milliseconds, and hiding it behind 30 minutes of silence would turn a cheap visible error into an invisible one.

**No silent fallback, in either direction.** Nothing here can move a task to a different provider; `ModelGateway.cs` is not modified at all. Rerouting an outage onto a paid provider is the 2026-07-14 390%-CPU incident with the arrow reversed. Provider choice stays 100% `Ai:Routes`-driven, and the Worker config now states prod intent explicitly instead of implying it.

**Verified against the real failure, not a mock**: local Ollama down, Worker started with `SENTRY_DSN` unset. Before, the backfill would make 38 calls; after, the log reads `enriching 38 user books` → `aborting after 0 enriched / 1 failed — provider 'ollama' is unavailable; the remaining candidates stay queued`, and exactly **one** HTTP request reached the wire (the half-open probe). The 38 candidate rows were still queued afterwards. That per-book re-check was added *because* the first live run exposed the gap: the startup probe opens the circuit on a 1-minute rung while the backfill only wakes at its 2-minute start delay, so the circuit is legitimately half-open by then and a single up-front gate let the whole batch begin. **1363 unit tests green** (79 new across `ProviderCircuitPolicyTests`, `ProviderHealthRegistryTests`, `AiRouteMapTests`, `AiProviderReadinessCheckTests`, `OllamaCircuitBreakerTests`, `MetadataWorkerGateTests`, `SentryEnvironmentTests`), including "20 concurrent callers at `RetryAt` yield exactly one probe" and "30 consecutive failures alarm once". Build + `dotnet format --verify-no-changes` clean. No migration. `Ai:ProviderHealth:Enabled=false` is a kill switch restoring byte-for-byte the previous behaviour.

Both new Sentry events carry explicit fingerprints keyed only on (event kind, provider) — without them `CaptureMessage` groups on the rendered message, which contains the volatile task list and retry duration, so every route edit would spawn a fresh issue and "resolved in release" would never stick.

<a id="2026-08-07-observability-sentry-leaked-sql-a-second-way-ef-core-error-e"></a>

## Observability — Sentry leaked SQL a second way: EF Core error EVENTS, not just breadcrumbs — backend — 2026-08-07

> Postmortem: [`docs/incidents/2026-08-07-sentry-scrubber-leaked-sql.md`](../incidents/2026-08-07-sentry-scrubber-leaked-sql.md)

Caught by the integration's own first day in production. Yesterday's PR (#445) found and fixed EF Core **breadcrumbs** carrying `Executed DbCommand … SELECT …` in their message; that fix was real but incomplete. EF Core also logs a *failed* command at **Error** level, and Sentry's `ILogger` integration turns any Error into an **event** — so the first live capture of the (separately real) `PUT /me/progress` failure arrived with `INSERT INTO reading_progresses (id, chapter_id, edition_id, locator, max_chapter_number, percent, site_id, updated_at, user_id) VALUES (@p0, …)` inline in the event message. Two distinct channels, one shared assumption: that nulling the structured `data` bag was where the SQL lived. It never was — EF interpolates the statement into the human-readable text on both paths.

Scope of the exposure, stated precisely: **no parameter values ever left the process** — `EnableSensitiveDataLogging` is off, so EF renders `@p0` / `'?'`, and Npgsql itself writes "Detail redacted as it may contain sensitive data" on the inner `PostgresException`. What did leave was statement shape and schema (table and column names). No book text, no reader identity. Still a promise this integration explicitly made and broke, and schema disclosure to a third party is not free.

Fix: `SentryScrubber.Scrub` now drops any event whose `Logger` starts with `Microsoft.EntityFrameworkCore`, plus a message probe for `Executed DbCommand` / `Failed executing DbCommand` so a re-categorised logger can't reopen the hole (`SentryScrubber.IsDatabaseCommandEvent`). **Dropping loses no signal**, which is what makes it the right call rather than a redaction exercise: the same failure is already reported by `ExceptionMiddleware` as a `DbUpdateException` carrying a full stack trace, the Npgsql SQLSTATE (`23505`) and the violated constraint name — everything needed to debug it, none of the SQL. A test locks that the middleware event survives while the EF command event dies.

The generalisable lesson, and the reason this is worth a CHANGELOG entry rather than a quiet patch: **a scrubber written against one egress path will be bypassed by the next one.** The original design rejected Sentry's OpenTelemetry exporter precisely because it bypasses `BeforeSend` — then shipped with two log-pipeline channels doing the same thing from the inside. Unit tests were green throughout both, because they asserted the scrubber's behaviour on the input shape we imagined rather than on what the SDK actually assembles. Only reading a real captured event found either one.

**1284 unit tests green** (3 new), build + `dotnet format --verify-no-changes` clean. No migration, no config, no behaviour change when `SENTRY_DSN` is unset.

<a id="2026-08-07-reader-reading-position-was-silently-lost-on-concurrent-save"></a>

## Reader — reading position was silently lost on concurrent saves (23505 upsert race) — backend — 2026-08-07

> Postmortem: [`docs/incidents/2026-08-07-reading-position-lost-23505.md`](../incidents/2026-08-07-reading-position-lost-23505.md)

Found by Sentry on its first day in production, which is the point of having installed it. `PUT /me/progress/{editionId}` was throwing `Npgsql.PostgresException: 23505: duplicate key value violates unique constraint "ix_reading_progresses_user_id_site_id_edition_id"` — ten times in four hours, from real readers, returning a 500 and **dropping the reader's position in the book**. Nothing crashed, no test failed, and the only prior symptom would have been a user saying "it forgot where I was".

Root cause is a textbook read-then-insert with no concurrency control: `UpsertProgress` queries `ReadingProgresses` for the row, and inserts when it finds none. One reader legitimately produces overlapping writes — the 30s session heartbeat, a `sendBeacon` on unload, an offline-queue flush after reconnect, or simply a second device — so two requests both see no row, both `INSERT`, and the loser violates the unique index. The window is milliseconds wide, which is why it only appears at real traffic and never in a test.

Fix: catch the unique violation and merge into the winner's row instead of failing. On `DbUpdateException` with SQLSTATE **23505** (matched via `PostgresErrorCodes.UniqueViolation`, not a message string, so it survives locale and constraint renames) the doomed insert is detached, the winner is re-read, and the client's write is applied to it — the exact update path we would have taken had we lost the race by one more millisecond. Critically, **the stale-write guard is re-applied against the WINNER's timestamp**, so recovering from the race still cannot move a reader backwards; and the monotonic `MaxChapterNumber` high-water mark (which feeds the RAG spoiler gate) is raised through the same shared `ApplyProgressUpdate` helper used by the normal path, so the two can never drift. A unique violation with no winning row (e.g. deleted in between) is rethrown rather than silently swallowed — that is not the race we know how to recover from.

Chosen over a native `INSERT … ON CONFLICT DO UPDATE` deliberately: the endpoint's semantics include an early return that echoes the *existing* row back when the client's timestamp is stale, which does not express cleanly in an upsert statement, and rewriting a hot path into raw SQL to fix a millisecond race is more risk than the race. The retry keeps every existing behaviour and touches one method.

**1289 unit tests green** (9 new, locking the high-water-mark monotonicity, the NULL-vs-ordinal-0 seeding rule, and that the recovery triggers on 23505 and nothing else — a foreign-key violation must still surface). Build + `dotnet format --verify-no-changes` clean. No migration.

<a id="2026-08-06-observability-sentry-for-api-worker-with-llm-agent-and-provi"></a>

## Observability — Sentry for API + Worker, with LLM agent and provider-routing spans — backend + infra — 2026-08-06

TextStack had **no error tracking at all**. OpenTelemetry has been wired since feat-0005, but it exports to an `aspire-dashboard` container that is profile-gated **off in production** — so for the whole life of the AI stack, prod telemetry has been going nowhere and nobody was alerted on anything. The trigger for fixing it was the 2026-07-14 incident (entry below): the Worker's `Ai:Routes` had no `pdf.parse` entry, so the user-PDF vision parse fell through to `Ai:DefaultProvider: ollama` and pegged the CPU-only Ollama container at **~390% for ~42 s/page across a 106-page book**. Nothing threw, nothing logged an error, no OpenAI traffic appeared, and the job simply produced zero chunks. **The failure mode was silence, and silence is exactly what a monitoring stack has to be taught to notice.** A reader of the write-up suggested emitting the resolved provider as a span attribute; that suggestion is the core of this change.

**The routing spans.** `ModelGateway.Route` and `ModelGateway.ResolvedPrimaryKey` each independently recomputed the same precedence — registry Primary → `Ai:Routes:{feature}` → `Ai:DefaultProvider` → literal `"openai"` — and neither could tell a *deliberate* route from a *silent* fallback, because the whole thing was one `??` chain that collapsed both into a string. Both now go through a single `ResolveRoute()` returning `(Key, Reason)`; the key expression is unchanged, so the resolved provider is provably identical (locked by a precedence theory in `ModelGatewayRouteReasonTests`). Every gateway call now attaches `ai.task`, `ai.provider.resolved` and `ai.provider.reason` (`route_matched` | `default_fallback`) to the ambient span — on the Sentry span *and* the OTel `Activity`, so the answer to "which model actually served this, and did anyone choose it on purpose?" comes from a trace instead of from a CPU graph. On top of that, an **expensive** task landing on `default_fallback` raises a Sentry warning outright: falling back to the default is normal and correct for most features, but for `pdf.parse`, `rag.summarize` and `podcast.script` (config `Ai:RouteAlarm:AlertOnDefaultRouteFor`) it is a defect by definition. **Throttling is load-bearing, not polish**: `pdf.parse` resolves once per page with parallelism 6, so that 106-page book would have raised 106 identical events — `AlarmThrottle` dedupes per `(task, provider, reason)` on a 60-minute cooldown (`Ai:RouteAlarm:CooldownMinutes`) while still firing the *first* hit immediately, so a bad deploy is visible within one page.

**Agent + RAG spans.** `AgentLoop.StreamAsync` is the single seam every agent runs through — Enrichment, Librarian, Tutor, StudyBuddy and the crews — because `RunAsync` is pure delegation, so one `using var trace = TraceScope.Start("agent.run", "ai.agent")` covers all of them (`using` is legal in an iterator and disposes on completion, `yield break`, throw *and* consumer abandonment). Each run reports `agent.name` (the `FeatureTag`, which is both the agent identity and the key `Ai:Routes` is indexed by, so the tag joins with routing config), `agent.model`, and measures for iterations/tokens-in/tokens-out/cost/duration; the outcome defaults to `error` and is set to `completed` or `budget_exhausted` at the three terminal paths, mapping 1:1 onto `AgentRunRecordFactory`'s statuses. `RagIndexingService` opens a `rag.index` span per book **after** the atomic claim (a lost claim is the common no-op and emits nothing) carrying `rag.kind`, `rag.book_id` and `rag.chunk_count`, and both `FailUserBookAsync`/`FailEditionAsync` — the single choke point for `rag_status = 3` — now raise a Sentry error carrying the `rag_error`. One deliberate exception: **`"indexing interrupted, retry"` is never sent**, because it fires on every deploy that lands mid-index and the sweep re-queues it — paging on a self-healing state on every release is how alerting dies.

**Provider failures.** `OllamaLlmClient` swallows non-2xx, timeouts and transport errors and returns an empty zero-token response — which is load-bearing (callers depend on it), and is precisely why those failures are invisible in `llm_traces`: `TracingDecorator` only ever sees a successful, empty answer. The swallow is untouched; each of the three branches now also calls `LlmFailureAlarm.Capture` with `ai.provider` / `ai.task` / `ai.failure` tags, on the same throttle. OpenAI failures need no such handling — they propagate to `TracingDecorator`'s two non-cancellation catches, the single choke point, which now reports them with the provider key (threaded in as a trailing optional ctor param so no existing test construction churned). Cancellation stays excluded on both paths: an SSE client disconnecting is not a model error.

**Why not `Sentry.OpenTelemetry`.** The obvious move — bridge the existing OTel spans into Sentry so there is one instrumentation — was rejected on evidence. Sentry deprecated that package, and its replacement (`Sentry.OpenTelemetry.Exporter`, on beta OTLP ingest) ships spans through the *OpenTelemetry* SDK, meaning `BeforeSend` never sees them. Our OTel spans carry `http.client_ip` (`ServiceCollectionExtensions.Hosting.cs`) and full SQL text (`SetDbStatementForText = true`), and there is no hook to strip either on the way out — that is a hard blocker for a reading app. It would also have forced Sentry's sample rate onto the shared `TracerProvider`, coupling the cost knob to the Aspire pipeline. Instead `TraceScope` dual-writes: one `Activity` (→ OTLP/Aspire, one added `AddSource` line is the *only* change to the existing pipeline) and one Sentry span (→ scrubbed at the edge).

**Noise and privacy.** `SentryScrubber` is an **allowlist, not a denylist** — every tag and extra not explicitly blessed is dropped or redacted. A denylist only stops the leaks someone remembered to enumerate; with an allowlist a future `span.SetTag("prompt", userText)` dies at the edge whether or not a reviewer caught it. On top of that: `SendDefaultPii = false`, `MaxRequestBodySize = None` (uploads are books, POST bodies are reader prompts), user identity blanked, `Authorization`/`Cookie`/`X-Admin-*` headers stripped, free text run through the existing `TraceRedactor` and truncated to 512 chars, breadcrumb `data` bags dropped wholesale, and `/health` + `/health/ready` sampled at 0.0. Client-error exceptions (`NotFoundException`, `ConflictException`, `ValidationException`, `DomainException`, `BudgetExceededException`, cancellation) are dropped — none can reach Sentry today because `ExceptionMiddleware` maps them to 4xx *without logging*, but the filter guards a future `LogError` on a validation path. Rate-limiter 429s are not exceptions and were never in scope. Sampling is deliberately asymmetric: `http.server` at `Sentry:TracesSampleRate` (0.2 prod, 1.0 dev), but `ai.agent` and `rag.index` **always at 1.0** — they are rare and they are the entire reason for this integration; sampling them at 0.2 would discard four of every five traces we added Sentry to see.

**Wiring and the no-op guarantee.** API takes `Sentry.AspNetCore` (6.8.0 ships a first-class `net10.0` TFM with zero dependencies); the Worker is a generic host with no request pipeline, so Sentry rides the ILogger provider — additive, the OTLP logging provider is untouched. Both call sites **skip the SDK entirely when `SENTRY_DSN` is empty** rather than initialising with a blank DSN (which still installs middleware and logs a startup diagnostic), so local dev, CI and forks are byte-identical to before. All the seam code (`SentrySdk.CaptureMessage`, `GetSpan`) is already inert against a disabled hub, so no `if (enabled)` guards leaked into `AgentLoop`, `ModelGateway` or `RagIndexingService`. `MinimumEventLevel = Error` is what actually captures unhandled errors: `ExceptionMiddleware` catches everything and returns a 500, so nothing ever reaches Sentry's own middleware — errors arrive via its `logger.LogError(ex, "Unhandled exception")`, confirmed in the verification below (the captured event's `logger` tag reads `Api.Middleware.ExceptionMiddleware`, `mechanism: SentryLogger`). Release plumbing is six lines of infra and no C#: `ARG GIT_SHA` → `ENV SENTRY_RELEASE` in both Dockerfiles (declared after the publish copy so a new SHA invalidates only that trivial layer, not the .NET build or the ~150 MB puppeteer install), `build.args` in compose, and `export GIT_SHA=$(git rev-parse --short HEAD)` in `deploy.yml` — `.dockerignore` excludes `.git`, so the build arg is the only way the SHA can get in, and without a release Sentry cannot do regression detection or tell you which deploy an issue started with.

**Verified end-to-end against the real DSN**, not just unit-tested: `POST /admin/diagnostics/sentry-test` (admin-gated by the existing path-based middleware; 401 unauthenticated) returned `{"eventId":"68aa5de7…","enabled":true}` and the API logged the same id; `POST /admin/diagnostics/sentry-test-error` returned 500 and produced a Sentry issue tagged **release `71c6b1da`, environment `Production`**, with `logger: Api.Middleware.ExceptionMiddleware` and only `Accept`/`Host`/`User-Agent` in the request headers — **the admin session cookie the request carried is absent**, user is empty, no body. A synthetic routing event confirmed the allowlist on the wire: `ai.task=pdf.parse`, `ai.provider.resolved=ollama`, `ai.provider.reason=default_fallback` survived; a `prompt` tag was **gone** and a `response` extra came through as `[redacted]`; an exception message containing an email arrived as `TextStack verify: synthetic failure for [redacted-email]`. One honest caveat: Sentry still shows a coarse **Geography (city-level)** derived server-side from the ingest connection IP — that is inferred at their edge, not sent in our payload, and in production it resolves to the datacenter rather than a reader. **1281 unit tests green** (35 new across `SentryBootstrapTests`, `SentryScrubberTests`, `AlarmThrottleTests`, `ModelGatewayRouteReasonTests` — including `TryEnter_RepeatedWithinCooldown_ClaimsOnce`, which replays 106 page-parallel calls and asserts exactly one event), `dotnet build` and `dotnet format --verify-no-changes` clean. No migration. No changes to web or mobile.

**Two findings from running it for real, both fixed/known before merge.** First, the scrubber leaked SQL. Pointing the local Worker at the branch build surfaced a genuine failure — the Ollama container wasn't running, so `MetadataBackfillWorker` threw 38 transport errors — and the resulting Sentry event's **breadcrumb trail carried `Executed DbCommand … SELECT m.feature_tag … FROM models`**. EF Core puts the SQL in the breadcrumb *message*, so nulling the structured `data` bag did nothing; this is the same `SetDbStatementForText` class of leak the PR avoided by rejecting Sentry's OTel exporter, quietly re-entering through the log pipeline. Fix: `ScrubBreadcrumb` now **drops EF Core command breadcrumbs entirely** (by category or by an `Executed DbCommand` message probe) rather than redacting them — a diagnostic breadcrumb is not worth shipping query text about what people are reading to a third party. Re-verified on a fresh live event: no `DbCommand`, no SQL. Second: those same 38 failures produced **exactly one Sentry event**, tagged `ai.provider=ollama`, `ai.task=bookmeta`, `ai.failure=transport` — the throttle working against a real running process rather than a unit test, and a failure mode that produced zero visibility before this PR. **To be exact about provenance, because the event itself is not:** this was a developer machine, not production — prod's `ollama` service was healthy throughout. The event nevertheless arrived tagged `environment: Production`, because the local `.env` sets `ASPNETCORE_ENVIRONMENT=Production`. That mislabelling is a real defect in its own right (a dev box writing into the production Sentry project under a production tag) and is fixed separately; it is called out here so nobody later reads this entry as a production incident.

**What we expect it to catch first**, in order of likelihood: a `default_fallback` on `rag.summarize` or `podcast.script` in the Worker (the same class of config drift as the original incident, now audible); Ollama timeouts during vocabulary distractor generation, which are today completely invisible because the client swallows them; and terminal RAG indexing failures on user PDFs, which until now surfaced only as a book stuck on a badge in the UI.

## RAG — deterministic tie-breaker on retrieval ORDER BY (repo now matches the article) — backend — 2026-07-15

The published RAG-determinism article claims hybrid retrieval orders with a deterministic tie-breaker (`ORDER BY score DESC, id`) — an audit found the fix was **missing from the repo**: all four hybrid queries in `RagService` (catalog + user-book, vector + lexical) ordered on the raw score/distance alone. <a id="2026-07-14-reliability-a-slow-hung-rag-parse-can-no-longer-wedge-the-in"></a>

## Reliability — a slow/hung RAG parse can no longer wedge the indexing worker — backend — 2026-07-14

> Postmortem: [`docs/incidents/2026-07-14-rag-parse-wedged-worker.md`](../incidents/2026-07-14-rag-parse-wedged-worker.md)

Follow-up to the durable-indexing work: the sweep loop `await`ed each book's chunk (vision parse) **inline**, so one slow or hung parse blocked the whole loop — no drain, and critically no stale-reclaim — until it returned. The mis-routed 74-minute Ollama parse wedged the worker exactly this way. Now the sweep **detaches** the parse to a background `Task.Run` gated by a `SemaphoreSlim(1)`: it dispatches at most one parse at a time (bounds paid vision spend) and the loop keeps running stale-reclaim + drain checks every 30 s, so a stuck parse can't wedge it. Restart-safe (the atomic `rag_indexing_started_at` claim runs before the parse, so a killed detached task is recovered by the stale sweep). **Hardened by adversarial QA** — the review caught (and this fixes) a **HIGH** semaphore leak: a DB exception between `Wait(0)` and dispatch would have leaked the slot permanently → the very silent-worker-wedge the change set out to kill; now a `try/finally` releases the slot on every non-dispatched path. `dotnet build` + **1120 unit** tests green. ## Reliability — "Ask this book" indexing no longer gets stuck + reading sessions survive a deleted book — backend + web — 2026-07-14

Two prod-confirmed reliability holes. **"Ask this book" could stick on "Preparing… 0/0" forever.** `POST /me/books/{id}/index` (and the catalog twin) atomically claimed `NotIndexed/Failed → Indexing`, then ran the chunking — for a PDF the **minutes-long `PdfVisionParser` vision parse** — **synchronously inside the HTTP request**, only returning `202` once it finished. When that request died (Cloudflare ~60-100s timeout, or the API container restarting on deploy — which is exactly how the OSCE workbook got stuck), the row was left `Indexing` with 0 chunks and **no terminal `Failed`**; the claim only re-claims from `NotIndexed/Failed`, so `Indexing` was a permanent dead end. Fixed by moving chunking **off the HTTP path into the Worker**, mirroring the enrichment-reliability pattern: the endpoint claims and returns `202 Indexing` immediately; a `RagIndexingService` executor does the work under an atomic `rag_indexing_started_at` claim and **always reaches a terminal state** (`chunkCount==0` / exception / cancellation → `Failed`); a `RagIndexingWorker` sweep (30s, one book/cycle to bound paid vision spend) drains queued books and reclaims dead-process `Indexing` rows (`started_at` older than 15 min) → `Failed`. The `ChapterEmbeddingWorker` chunk→embed→`Ready` hand-off is unchanged; catalog and user-book paths unify on the one executor. Migration adds nullable `rag_indexing_started_at` (+ partial sweep indexes) on `user_books` + `editions`. **Hardened by adversarial QA**: the embedder now marks a book `Failed` when it permanently poisons a chunk (previously `embedded < chunk_count` stranded it `Indexing` forever, bypassing the `chunk_count=0` sweep); the executor's chunk-count stamp is a guarded `WHERE rag_status=1` UPDATE (a stale-swept `Failed` row can't be clobbered); `embedded_count` is recomputed from actual rows after chunking (was a blind `0`, losing an embedder-drains-first race); and cancellation writes "indexing interrupted, retry" instead of a misleading "no chapters". Known follow-up (accepted): full concurrency/detach for a multi-Worker deployment (the model assumes a single Worker today).

Separately, **reading sessions for a deleted book stopped flooding 500s.** After re-uploading a book (old id gone), the client's queued/`sendBeacon` sessions kept resubmitting for the dead `user_book_id`, hitting a Postgres `23503` FK violation → unhandled `DbUpdateException` → 500, retried forever. Now `ReadingSessionService.SubmitAsync` existence-checks the referenced book (owned + live user book, or a real edition) and returns **404** for a gone book (with a belt-and-suspenders `23503` catch → benign ack), and the client **prunes** the queued session on a 404 instead of re-queuing it (5xx/network still retry). `dotnet build` + **1113 unit** tests (+ session/RAG integration tests: `202 Indexing`-without-chunking, session `404`); web `tsc`/`vite build` + **684 web** vitest. The live chunk→embed→`Ready` round-trip verifies on prod (arm64 worker SIGILL + no local OpenAI key); already-stuck prod rows are cleared by a one-off backfill at deploy.

## User books — metadata enrichment is reliable + visible (description/genre/year) — backend + web + mobile — 2026-07-13

## Ops — root cause: the nightly backup was leaking 156 GB of orphaned pgdata volumes — infra — 2026-07-10

> Postmortem: [`docs/incidents/2026-07-10-backup-leaked-156gb.md`](../incidents/2026-07-10-backup-leaked-156gb.md)

The actual root cause behind the flapping backup (the self-diagnostics below were added to *find* this). Prod's Docker data-root lives on a **separate `/mnt/data` partition** (not `/`, which `df -h /` alone hides) and it had hit **100% / 0 bytes free** — 183 GB used, **156 GB of it 57 dangling anonymous `pgdata` volumes**. `backup-verify.sh` spins a throwaway `pgvector` postgres each run; postgres declares an anonymous `VOLUME /var/lib/postgresql/data`. On a killed/timed-out run `--rm` never fired and the cleanup did `docker rm -f` **without `-v`** → one full pgdata volume leaked per run. 34 days × daily ≈ 156 GB → the docker root filled → a fresh throwaway postgres could no longer `initdb` → **the backup broke the very verify step that had been creating the volumes** — a self-reinforcing failure. Real prod data was never at risk (postgres + storage bind-mount to `/`, which was at 61%); only the anonymous verify volumes bloated `/mnt/data`. Fix: `docker rm -f` → **`docker rm -fv`** (both the trap cleanup and the leaked-container reap) so the anonymous volume dies with its container, plus a `docker volume prune -f` catch-all for SIGKILL'd runs the trap can't cover (named volumes are untouched by prune). Remediated live: `docker volume prune` reclaimed **163 GB**, `/mnt/data` 100% → 17%. Diagnosed the hard way — the box was also unreachable for a stretch (a clean manual reboot, not a crash; a full disk still lets you SSH in, so an SSH *connect*-timeout is a host-offline signal, not disk).

## Ops — backup verify self-diagnoses failures + reaps leaked containers — infra — 2026-07-10

The daily backup's restore-verify step (`infra/scripts/backup-verify.sh`, which restores the dump into a throwaway pgvector container) was failing with a bare `postgres did not become ready` that hid the real cause. <a id="2026-07-09-auth-fix-spurious-unauthorized-mid-session-refresh-token-sta"></a>

## Auth — fix spurious "Unauthorized" mid-session (refresh-token stampede) — web — 2026-07-09

> Postmortem: [`docs/incidents/2026-07-09-refresh-token-stampede.md`](../incidents/2026-07-09-refresh-token-stampede.md)

Fixed the reader dead-ending on **"Error loading chapter — Unauthorized"** after ~an hour, even though the user was still signed in (Google/email). Root cause: the access token expires at 60 min, and the reader fires many authenticated requests in parallel (chapter, book, progress, bookmarks…), so they all 401 at the same instant and each independently called `/auth/refresh`. The server **rotates** the refresh token on every refresh (deletes the presented token, issues a new one), so only the first concurrent refresh won — the rest presented the now-deleted token and got 401, surfacing as a spurious mid-session logout. Fix: `refreshToken()` in `apps/web/src/api/auth.ts` is now **single-flight** — concurrent callers share one in-flight `/auth/refresh`, so there's exactly one rotation and one fresh cookie, then every caller retries. This makes silent refresh reliable, so an active user stays signed in across the full rotating refresh-token window (i.e. until they explicitly log out or are inactive past the TTL) instead of being bounced hourly. Pure client change, no backend/token-config change. `tsc` clean, `vite build` green, **22 auth/api vitest** green (3 new: concurrent-dedup, fresh-request-after-settle, lock-clears-on-failure). Mobile (`apps/mobile/src/lib/api.ts`) already single-flights refresh — not affected.
